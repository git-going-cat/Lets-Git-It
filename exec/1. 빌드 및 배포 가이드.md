## 5. 환경 변수 설정

각 컴포넌트 `.env.example`을 복사해 `.env`를 만들고 실제 값을 입력합니다.  
`.env` 파일은 `.gitignore`에 등록되어 있으며 Git에 커밋되지 않습니다.

## 6. 빌드

### 6-1. 백엔드 (BE)

```bash
cd BE/letsgitit

# 테스트 제외 빌드 (JAR 생성)
./gradlew bootJar -x test

# 코드 스타일 검사 (Spotless + Naver Eclipse Formatter)
./gradlew spotlessCheck

# 테스트 실행 (H2 인메모리 DB 사용)
./gradlew test -Dspring.profiles.active=test
```

빌드 결과물: `BE/letsgitit/build/libs/letsgitit-0.0.1-SNAPSHOT.jar`

> QueryDSL 생성 코드는 `build/generated/querydsl` 아래에 생성됩니다.  
> Spotless는 Naver Eclipse 포맷터(`style/naver-eclipse-formatter.xml`) 기반으로 검사합니다.

---

### 6-2. 프론트엔드 (FE)

```bash
cd FE

# 의존성 설치 (CI 환경에서는 npm ci 사용)
npm install

# 개발 서버 실행
npm run dev       # http://localhost:5173

# 프로덕션 빌드 (TypeScript 컴파일 후 Vite 번들링)
npm run build

# 빌드 결과 로컬 미리보기
npm run preview
```

빌드 결과물: `FE/dist/`

> pre-commit hook(husky + lint-staged)이 설정되어 있어 커밋 시 Prettier/ESLint가 자동 실행됩니다.

---

### 6-3. AI

```bash
cd AI

# 가상환경 생성 및 활성화
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 의존성 설치
pip install -r requirements.txt

# 벡터 임베딩 최초 생성 (최초 1회, 배포 전 필수)
python scripts/ingest.py --index

# 개발 서버 실행
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

> `AI/data/embeddings.npy` 파일이 없으면 `deploy-ai.sh`가 실행을 중단합니다.  
> 임베딩 파일은 Git에 포함되지 않으므로 서버 최초 구성 시 반드시 생성해야 합니다.

## 9. 배포

### 9-1. CI/CD 자동 배포 (GitLab CI)

`.gitlab-ci.yml` 기반 2단계 파이프라인:

| Stage | 실행 시점 | 설명 |
|-------|---------|------|
| `ci` | MR(Merge Request) 발생 시 | 테스트 및 린트 검사 |
| `deploy` | `develop` / `prod` 브랜치 push 시 | 서버 자동 배포 |

**브랜치 → 환경 매핑**:

| 브랜치 | 배포 환경 | Runner 태그 |
|--------|---------|------------|
| `develop` | 개발계 | `[dev]` |
| `prod` | 운영계 | `[prod]` |

**CI 검사 항목**:

| Job | 이미지 | 실행 내용 |
|-----|--------|---------|
| `be-ci` | `amazoncorretto:17-alpine` | `./gradlew test` + `./gradlew spotlessCheck` |
| `fe-ci` | `node:24.13.0` | `npm ci` → `npm run lint` → `npm run format` → `npm run test` |

**배포 트리거 파일 목록**:

| Job | 트리거되는 파일 변경 |
|-----|-----------------|

## 10. 배포 특이사항

### 블루/그린 무중단 배포 (BE)

- `deploy-be.sh` 실행 시 `spring-blue` ↔ `spring-green` 컨테이너를 번갈아 사용
- 현재 활성 색상은 `INFRA/.active_color` 파일에 저장됨 (최초 기본값: `blue`)
- 신규 컨테이너 헬스체크(`GET /actuator/health`) 통과 확인 후 nginx upstream 파일 교체 → `nginx -s reload`
- 헬스체크: **최대 100초** (5초 간격 × 20회), 실패 시 신규 컨테이너 중단 및 롤백

### FE 빌드 특이사항

- Docker 컨테이너 내부에서 `npm run build` 후 호스트의 `fe-dist/` 디렉터리로 dist 파일 추출
- `VITE_WS_URL`은 Docker build-arg(`--build-arg`)로 명시적 전달
- 나머지 `VITE_*` 환경변수는 `deploy-fe.sh`가 `FE/.env`를 소스하여 처리
- Nginx는 `fe-dist/`를 Document Root(`/usr/share/nginx/html`)로 마운트

### AI 배포 전 필수 조건

- `AI/data/embeddings.npy` 파일이 반드시 존재해야 배포 가능
- 파일이 없으면 `deploy-ai.sh` 조기 종료 (exit 1)
- **최초 생성 명령**: `python scripts/ingest.py --index` (가상환경 활성화 후 실행)

### SSL/TLS

- Let's Encrypt 인증서 사용 (Certbot으로 발급)
- Nginx 컨테이너에 `/etc/letsencrypt` 볼륨 마운트
- 인증서/키 경로는 `INFRA/.env.nginx`의 `SSL_CERT`, `SSL_KEY`로 지정
- HTTP(80)는 HTTPS(443)로 301 리다이렉트

### Spring 프로파일 전환

- 환경 변수 `SPRING_PROFILES_ACTIVE`로 제어 (`dev` | `prod`)
- `INFRA/.env`에서 설정하며 Docker Compose가 Spring 컨테이너에 주입

### 로그 수집

- Promtail이 Docker 컨테이너 로그(`/var/lib/docker/containers`)를 Loki로 전달
- Spring Boot Actuator `/actuator/prometheus` 엔드포인트에서 Prometheus가 15초 간격으로 스크랩
- Grafana에서 Prometheus(메트릭) + Loki(로그) 통합 조회 (로그 보존: 7일)

## 12. WireGuard VPN 세팅

로컬 개발 환경에서 EC2 MySQL/Redis에 직접 접근하기 위해 WireGuard VPN을 구성합니다.  
팀원은 WireGuard 앱을 켜두면 VPN 연결이 유지되며, 연결된 상태에서만 `10.0.0.1` 로 DB/Redis 접근이 가능합니다.

### 서버 설치

```bash
sudo apt update
sudo apt install -y wireguard
```

### 서버 키 쌍 생성

```bash
wg genkey | sudo tee /etc/wireguard/server_private.key
sudo cat /etc/wireguard/server_private.key | wg pubkey | sudo tee /etc/wireguard/server_public.key
sudo chmod 600 /etc/wireguard/server_private.key
```

### 서버 설정 파일 작성

```bash
sudo nano /etc/wireguard/wg0.conf
```

```ini
[Interface]
Address = 10.0.0.1/24
ListenPort = 51820
PrivateKey = <서버_개인키>

PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <팀원1_공개키>
AllowedIPs = 10.0.0.2/32

[Peer]
PublicKey = <팀원2_공개키>
AllowedIPs = 10.0.0.3/32
```

### IP 포워딩 활성화

```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf
```

### EC2 보안그룹 및 ufw 포트 오픈

AWS 콘솔 → EC2 → 보안 그룹 → 인바운드 규칙 편집에서 아래 항목 추가:

| 유형 | 포트 | 소스 |
|------|------|------|
| 사용자 지정 UDP | 51820 | 0.0.0.0/0 |

```bash
sudo ufw allow 51820/udp
sudo ufw status
```

### WireGuard 서비스 시작

```bash
sudo wg-quick up wg0
sudo systemctl enable wg-quick@wg0
sudo wg show
```

### 팀원 클라이언트 키 쌍 생성

팀원이 각자 로컬에서 키를 생성하고 공개키만 서버 관리자에게 전달합니다.

```bash
# 팀원 로컬에서 실행 (Windows: PowerShell, Mac/Linux: 터미널)
wg genkey | tee client_private.key | wg pubkey > client_public.key
cat client_public.key   # 이 값을 관리자에게 전달
```

전달받은 공개키를 `wg0.conf`의 `[Peer]`에 추가 후 재시작합니다.

```bash
sudo wg-quick down wg0
sudo wg-quick up wg0
```

### 팀원 클라이언트 설정 파일 배포

아래 내용을 팀원에게 배포하며, 팀원은 [WireGuard 공식 앱](https://www.wireguard.com/install/)을 설치한 후 import합니다.

```ini
[Interface]
Address = 10.0.0.X/24
PrivateKey = <팀원_개인키>

[Peer]
PublicKey = <서버_공개키>
Endpoint = <개발계_EC2_IP>:51820
AllowedIPs = 10.0.0.0/24
PersistentKeepalive = 25
```

### VPN 연결 테스트

VPN 연결 후 아래 명령으로 DB/Redis 접근을 확인합니다.

```bash
mysql -h 10.0.0.1 -P 3306 -u letsgit -p
redis-cli -h 10.0.0.1 -p 6379 ping
redis-cli -h 10.0.0.1 -p 6380 ping
redis-cli -h 10.0.0.1 -p 6381 ping
```

### 로컬 개발용 application-dev.yml 예시

VPN 연결 상태에서만 동작합니다.

```yaml
spring:
  datasource:
    url: jdbc:mysql://10.0.0.1:3306/letsgit_dev
    username: letsgit
    password: <개발계_비밀번호>
  data:
    redis:
      host: 10.0.0.1
      port: 6379
```

## 13. GitLab Runner CI/CD 세팅

### CI/CD 배포 방식

GitLab Registry에 이미지를 push/pull하는 대신, EC2에서 직접 `git pull` 후 빌드하는 방식을 사용합니다.

```
브랜치 push / MR merge
→ GitLab Runner 캐치
→ EC2에서 git pull
→ 배포 스크립트 실행 (deploy-be.sh / deploy-fe.sh / deploy-ai.sh)
```

### GitLab Runner 설치 및 등록

```bash
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt install -y gitlab-runner
sudo gitlab-runner register
```

프롬프트 입력값:

| 항목 | 개발계 | 운영계 |
|------|--------|--------|
| GitLab instance URL | `https://lab.ssafy.com` | `https://lab.ssafy.com` |
| Registration token | GitLab 프로젝트에서 확인 | GitLab 프로젝트에서 확인 |
| Description | `dev-runner` | `prod-runner` |
| Tags | `dev` | `prod` |
| Executor | `shell` | `shell` |

### GitLab Runner SSH 키 등록

Runner가 GitLab 레포를 pull 받으려면 SSH Deploy Key가 필요합니다.

```bash
# gitlab-runner 유저로 전환
sudo su - gitlab-runner

# SSH 키 생성
ssh-keygen -t ed25519 -C "gitlab-runner-dev"

# 공개키 출력
cat ~/.ssh/id_ed25519.pub
```

출력된 공개키를 GitLab 프로젝트의 **Settings → Repository → Deploy keys** 에 등록합니다.

### EC2에 레포 최초 클론

CI/CD 파이프라인 실행 전 EC2에 레포를 먼저 클론해둬야 합니다.

```bash
# gitlab-runner 유저로 전환
sudo su - gitlab-runner

# 개발계
git clone git@lab.ssafy.com:s14-final/S14P31A304.git /home/ubuntu/develop/S14P31A304

# 운영계
# git clone git@lab.ssafy.com:s14-final/S14P31A304.git /home/ubuntu/S14P31A304
```

### 파이프라인 동작 확인

등록 후 아래 항목으로 정상 동작을 확인합니다.

- `develop` 브랜치에 push → 개발계 `deploy` stage 실행 확인
- `prod` 브랜치에 push → 운영계 `deploy` stage 실행 확인
- GitLab 프로젝트 → **CI/CD → Pipelines** 에서 Runner 태그 및 실행 로그 확인
