git-fast-import(1)
==================

NAME
----
git-fast-import - 빠른 Git 데이터 임포터 백엔드


SYNOPSIS
--------
[verse]
frontend | 'git fast-import' [<options>]

DESCRIPTION
-----------
이 프로그램은 일반적으로 사용자가 직접 실행하기를 원하는 것이 아닙니다.
대부분의 일반 사용자는 기존 프론트엔드 프로그램 중 하나를 사용하기를 원하며,
이 프로그램은 특정 유형의 외부 소스를 파싱하여 해당 소스에 저장된 내용을
'git fast-import'로 전달합니다.

fast-import는 표준 입력에서 혼합된 명령/데이터 스트림을 읽고
현재 저장소에 하나 이상의 팩파일을 직접 작성합니다.
표준 입력에서 EOF를 받으면, fast-import는 업데이트된 브랜치 및 태그 ref들을 작성하여
새로 임포트된 데이터로 현재 저장소를 완전히 업데이트합니다.

fast-import 백엔드 자체는 비어 있는 저장소(이미 'git init'으로 초기화된 저장소)로
임포트하거나 기존에 채워진 저장소를 점진적으로 업데이트할 수 있습니다.
특정 외부 소스에서 점진적 임포트가 지원되는지 여부는 사용 중인
프론트엔드 프로그램에 따라 다릅니다.


OPTIONS
-------

--force::
	기존 브랜치를 강제로 업데이트합니다. 새 커밋이 이전 커밋을
	포함하지 않아 커밋이 손실되더라도 업데이트합니다.

--quiet::
	--stats로 표시되는 출력을 비활성화하여 fast-import가 성공 시
	일반적으로 조용하게 만듭니다. 그러나 임포트 스트림에 사용자 출력
	(예: `progress` 지시자)을 표시하기 위한 지시자가 있는 경우,
	해당 메시지는 여전히 표시됩니다.

--stats::
	fast-import가 생성한 객체, 해당 객체가 저장된 팩파일,
	그리고 이 실행 동안 fast-import가 사용한 메모리에 대한
	기본 통계를 표시합니다. 이 출력 표시는 현재 기본값이지만,
	--quiet로 비활성화할 수 있습니다.

--allow-unsafe-features::
	`feature` 또는 `option` 명령을 사용하여 많은 명령줄 옵션을
	fast-import 스트림 자체의 일부로 제공할 수 있습니다. 그러나 이러한
	옵션 중 일부는 안전하지 않습니다(예: fast-import가 저장소 외부의
	파일시스템에 접근하도록 허용하는 경우). 이러한 옵션은 기본적으로
	비활성화되어 있지만, 명령줄에서 이 옵션을 제공하여 허용할 수 있습니다.
+
이 옵션은 현재 `export-marks`, `import-marks`, 및 `import-marks-if-exists`
feature 명령에만 영향을 줍니다.
+
fast-import 스트림을 생성하는 프로그램을 신뢰하는 경우에만 이 옵션을 활성화하세요!
이 옵션은 `import` 기능을 사용하는 원격 헬퍼에 대해 자동으로 활성화됩니다.
이는 해당 헬퍼가 자체 코드를 실행하는 것으로 이미 신뢰되기 때문입니다.

`--signed-tags=<mode>`::
	서명된 태그를 처리하는 방법을 지정합니다. 아래의
	`--signed-commits=<mode>`와 동일하게 작동합니다. 서명된 커밋의 경우와
	마찬가지로, 기본 모드는 `verbatim`입니다.

`--signed-commits=<mode>`::
	서명된 커밋을 처리하는 방법을 지정합니다. 다음 <mode>들이 지원됩니다:
+
* `verbatim`: 기본 모드로, 커밋 서명을 조용히 임포트합니다.
* `warn-verbatim`: 서명을 임포트하지만 경고를 표시합니다.
* `abort`: 서명된 커밋을 만나면 프로그램이 종료됩니다.
* `strip`: 커밋을 조용히 서명 해제합니다.
* `warn-strip`: 커밋을 서명 해제하지만 경고를 표시합니다.
* `strip-if-invalid`: 서명을 검증하고, 유효하지 않으면 서명을 제거하고
  경고를 표시합니다. 검증은 linkgit:git-verify-commit[1]과 동일한 방식으로
  수행됩니다.
* `sign-if-invalid[=<keyid>]`: `strip-if-invalid`와 유사하게, 커밋 서명을
  검증하고 유효하지 않은 서명을 새로 생성된 서명으로 대체합니다. 유효한
  서명은 변경되지 않습니다. `<keyid>`가 제공되면 해당 키를 사용하여 서명하고,
  그렇지 않으면 구성된 기본 서명 키를 사용합니다.
* `abort-if-invalid`: 검증할 수 없는 서명된 커밋을 만나면 프로그램이
  종료됩니다.

Frontend를 위한 옵션
~~~~~~~~~~~~~~~~~~~~~

--cat-blob-fd=<fd>::
	`get-mark`, `cat-blob`, 및 `ls` 쿼리에 대한 응답을 `stdout` 대신
	파일 디스크립터 <fd>에 씁니다. 최종 사용자용으로 의도된
	`progress` 출력을 다른 출력과 분리할 수 있습니다.

--date-format=<fmt>::
	프론트엔드가 `author`, `committer` 및 `tagger` 명령에서
	fast-import에 제공할 날짜의 형식을 지정합니다. 지원되는 형식과
	구문에 대한 자세한 내용은 아래의 ``Date Formats''를 참조하십시오.

--done::
	스트림 끝에 `done` 명령이 없으면 오류로 종료합니다. 이 옵션은
	프론트엔드가 스트림 작성을 시작하기 전에 종료되는 오류를 탐지하는 데
	유용할 수 있습니다.

Marks 파일 위치
~~~~~~~~~~~~~~~~~~~~~~~~

--export-marks=<file>::
	완료 시 내부 marks 테이블을 <file>에 덤프합니다. Marks는 `:markid SHA-1`
	형식으로 각 줄마다 작성됩니다. 프론트엔드는 이 파일을 사용하여
	임포트가 완료된 후 검증하거나, 점진적 실행에 걸쳐 marks 테이블을
	저장할 수 있습니다. <file>은 체크포인트 (또는 완료) 시에만 열리고
	잘립니다. 따라서 --import-marks와 동일한 경로를 안전하게 지정할 수 있습니다.

--import-marks=<file>::
	어떤 입력도 처리하기 전에 <file>에 지정된 marks를 로드합니다.
	입력 파일은 존재해야 하고, 읽을 수 있어야 하며, --export-marks에서
	생성된 것과 동일한 형식을 사용해야 합니다. 여러 개의 marks 세트를
	임포트하기 위해 여러 옵션을 제공할 수 있습니다. mark가 다른 값으로
	정의된 경우, 마지막 파일이 우선합니다.

--import-marks-if-exists=<file>::
	--import-marks와 유사하지만, 오류를 발생시키는 대신 파일이 존재하지
	않으면 조용히 건너뜁니다.

--relative-marks::
--no-relative-marks::
	--relative-marks를 지정한 후 --import-marks= 및 --export-marks=로
	지정된 경로는 현재 저장소의 내부 디렉토리에 상대적입니다.
	git-fast-import에서는 경로가 `.git/info/fast-import`에 상대적이라는
	의미입니다. 그러나 다른 임포터는 다른 위치를 사용할 수 있습니다.
+
상대 및 비상대 marks는 --(import|export)-marks= 옵션과 --(no-)-relative-marks를
	상호 교환하여 결합할 수 있습니다.

Submodule Rewriting
~~~~~~~~~~~~~~~~~~~

--rewrite-submodules-from=<name>:<file>::
--rewrite-submodules-to=<name>:<file>::
  <name>으로 지정된 서브모듈의 객체 ID를 from <file>에서 사용된 값에서
	to <file>에서 사용된 값으로 다시 작성합니다. from marks는
	`git fast-export`에 의해 생성되었어야 하며, to marks는
	해당 서브모듈을 임포트할 때 `git fast-import`에 의해 생성되었어야 합니다.
+
<name>은 콜론 문자를 포함하지 않는 임의의 문자열일 수 있지만,
	대응하는 marks를 지정할 때 두 옵션 모두에 대해 동일한 값이 사용되어야 합니다.
	다른 <name> 값을 사용하여 여러 서브모듈을 지정할 수 있습니다.
	대응하는 쌍으로 이러한 옵션을 사용하지 않는 것은 오류입니다.
+
이 옵션들은 주로 저장소를 다른 해시 알고리즘으로 변환할 때 유용합니다.
	이 옵션들이 없으면, fast-import는 서브모듈을 만나도 새 해시 알고리즘으로
	객체 ID를 작성할 방법이 없기 때문에 실패합니다.

성능 및 압축 튜닝
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

--active-branches=<n>::
	동시에 유지할 활성 브랜치의 최대 개수입니다.
	자세한 내용은 아래의 ``Memory Utilization''을 참조하십시오.
	기본값은 5입니다.

--big-file-threshold=<n>::
	fast-import가 델타를 생성하려고 시도하는 블롭의 최대 크기입니다.
	바이트 단위로 표현됩니다. 기본값은 512m (512 MiB)입니다.
	일부 임포터는 메모리가 제한된 시스템에서 이 값을 낮추고 싶어할 수 있습니다.

--depth=<n>::
	블롭 및 트리 델타화에 대한 최대 델타 깊이입니다.
	기본값은 50입니다.

--export-pack-edges=<file>::
	팩파일을 생성한 후, 팩파일의 파일 이름과 해당 팩파일에 기록된
	각 브랜치의 마지막 커밋을 나열하는 데이터 줄을 <file>에 출력합니다.
	이 정보는 총 객체 집합이 4 GiB 팩파일 제한을 초과하는 프로젝트를
	임포트한 후에 유용할 수 있습니다. 해당 커밋은 'git pack-objects'
	호출 시 엣지 포인트로 사용될 수 있습니다.

--max-pack-size=<n>::
	각 출력 팩파일의 최대 크기입니다.
	기본값은 무제한입니다.

fastimport.unpackLimit::
	linkgit:git-config[1] 참조

PERFORMANCE
-----------
fast-import의 설계는 최소한의 메모리 사용량과 처리 시간으로
대규모 프로젝트를 임포트할 수 있도록 합니다. 프론트엔드가
fast-import를 따라잡고 일정한 데이터 스트림을 공급할 수 있다고 가정하면,
10년 이상의 히스토리를 보유하고 100,000개 이상의 개별 커밋을 포함하는
프로젝트의 임포트 시간은 일반적으로 상당히 겸손한 하드웨어(~2007년 기준
2,000 USD)에서 1-2시간 내에 완료됩니다.

대부분의 병목 현상은 외부 소스 데이터 액세스(소스가 수정본을 충분히
빨리 추출할 수 없음) 또는 디스크 IO(fast-import는 디스크가 데이터를
수용하는 만큼 빠르게 씁니다)에 있는 것으로 보입니다. 소스 데이터가
목적지 Git 저장소와 다른 드라이브에 저장되어 있으면(IO 충돌이 적기 때문에)
임포트는 더 빨라집니다.


DEVELOPMENT COST
----------------
fast-import의 일반적인 프론트엔드는 약 200줄의 Perl/Python/Ruby 코드로
구성됩니다. 대부분의 개발자는 fast-import나 Git 자체에 처음 접하더라도
몇 시간 내에 작동하는 임포터를 만드는 데 성공했으며, 이는 대부분의
변환 도구가 일회용(한 번 사용하고 다시 보지 않음)이라는 점을 감안할 때
이상적인 상황입니다.


PARALLEL OPERATION
------------------
'git push' 또는 'git fetch'와 마찬가지로, fast-import로 처리되는
임포트는 병렬 `git repack -a -d` 또는 `git gc` 호출, 또는 다른 Git
작업(loose 객체는 fast-import에서 사용되지 않으므로 'git prune' 포함)과
함께 안전하게 실행할 수 있습니다.

fast-import는 적극적으로 임포트하는 브랜치 또는 태그 ref를 잠그지 않습니다.
임포트 후 ref 업데이트 단계 동안, fast-import는 각 기존 브랜치 ref를
테스트하여 업데이트가 fast-forward 업데이트(ref에 저장된 커밋이 작성될
커밋의 새 히스토리에 포함됨)인지 확인합니다. 업데이트가 fast-forward
업데이트가 아니면, fast-import는 해당 ref를 업데이트하는 것을 건너뛰고
대신 경고 메시지를 출력합니다. fast-import는 항상 모든 브랜치 ref를
업데이트하려고 시도하며, 첫 번째 실패 시 중단되지 않습니다.

브랜치 업데이트는 --force로 강제할 수 있지만, 이는 다른 조용한 저장소에서만
사용하는 것이 좋습니다. `--force`는 처음 비어 있는 저장소로의 임포트에는
필요하지 않습니다.


TECHNICAL DISCUSSION
--------------------
fast-import는 메모리에서 브랜치 세트를 추적합니다. 임포트 프로세스 중
언제든지 `commit` 명령을 입력 스트림으로 보내어 어떤 브랜치든 생성하거나
수정할 수 있습니다. 이 설계는 프론트엔드 프로그램이 무제한의 브랜치를
동시에 처리하고 소스 데이터에서 사용 가능한 순서대로 커밋을 생성할 수
있도록 합니다. 이는 또한 프론트엔드 프로그램을 상당히 단순화합니다.

fast-import는 현재 작업 디렉토리나 그 안의 어떤 파일도 사용하거나
수정하지 않습니다. (하지만 `GIT_DIR`에서 참조되는 현재 Git 저장소는
업데이트합니다.) 따라서 임포트 프론트엔드는 외부 소스에서 파일 수정본을
추출하는 등 자체 용도로 작업 디렉토리를 사용할 수 있습니다. 작업 디렉토리에
대한 이러한 무관심은 fast-import가 브랜치 간 전환 시 비용이 많이 드는
파일 업데이트 작업을 수행할 필요가 없어 매우 빠르게 실행될 수 있도록 합니다.

INPUT FORMAT
------------
raw file data(Git이 해석하지 않는)를 제외하고 fast-import 입력 형식은
텍스트(ASCII) 기반입니다. 이 텍스트 기반 형식은 프론트엔드 프로그램의
개발 및 디버깅을 단순화하며, 특히 Perl, Python 또는 Ruby와 같은
고급 언어를 사용하는 경우에 그렇습니다.

fast-import는 입력에 매우 엄격합니다. 여기서 SP는 *정확히* 하나의
공백을 의미합니다. 마찬가지로 LF는 하나의 (그리고 오직 하나의) 줄바꿈이고
HT는 하나의 (그리고 오직 하나의) 수평 탭입니다. 추가 공백 문자를 제공하면
브랜치 이름이나 파일 이름에 선행 또는 후행 공백이 포함되거나, unexpected
input을 만났을 때 fast-import가 조기에 종료되는 등 예상치 못한 결과가
발생할 수 있습니다.

Stream Comments
~~~~~~~~~~~~~~~
프론트엔드 디버깅을 돕기 위해 fast-import는 `#`(ASCII 파운드/해시)으로
시작하는 모든 줄을 줄 끝 `LF`까지 무시합니다. 주석 줄은 LF를 포함하지
않는 임의의 바이트 시퀀스를 포함할 수 있으므로, fast-import 데이터 스트림을
검사할 때 유용한 프론트엔드별 상세 디버깅 정보를 포함하는 데 사용될 수 있습니다.

Date Formats
~~~~~~~~~~~~
다음 날짜 형식이 지원됩니다. 프론트엔드는 --date-format=<fmt>
명령줄 옵션에서 형식 이름을 전달하여 이 임포트에 사용할 형식을
선택해야 합니다.

`raw`::
	이것은 Git 네이티브 형식이며 `<time> SP <offutc>`입니다.
	--date-format이 지정되지 않은 경우 fast-import의 기본 형식입니다.
+
이벤트의 시간은 `<time>`으로 UNIX 에포크(1970년 1월 1일 자정, UTC) 이후
	초 단위로 지정되며 ASCII 10진수 정수로 작성됩니다.
+
로컬 오프셋은 `<offutc>`로 UTC로부터의 양수 또는 음수 오프셋으로
	지정됩니다. 예를 들어 EST(UTC보다 5시간 뒤)는 `<tz>`에서
	``-0500''으로 표현되는 반면 UTC는 ``+0000''입니다.
	로컬 오프셋은 `<time>`에 영향을 주지 않습니다. 타임스탬프를
	표시하는 형식 루틴을 돕기 위한 권고로만 사용됩니다.
+
소스 자료에 로컬 오프셋을 사용할 수 없는 경우, ``+0000'' 또는
	가장 일반적인 로컬 오프셋을 사용하십시오. 예를 들어 많은 조직에는
	동일한 위치와 시간대에 있는 사용자만 액세스했던 CVS 저장소가 있습니다.
	이 경우 UTC로부터의 합리적인 오프셋을 가정할 수 있습니다.
+
`rfc2822` 형식과 달리, 이 형식은 매우 엄격합니다. 형식에 약간의
	변형이라도 있으면 fast-import가 값을 거부하고, 숫자 값에 대한
	몇 가지 검증이 수행될 수도 있습니다.

`raw-permissive`::
	`raw`와 동일하지만 숫자 에포크 및 로컬 오프셋에 대한 검증이
	수행되지 않습니다. 이는 기존 히스토리를 필터링하거나 임포트할 때
	(예: 잘못된 시간대 값 포함) 유용할 수 있습니다.

`rfc2822`::
	RFC 2822에 설명된 표준 날짜 형식입니다.
+
예시 값은 ``Tue Feb 6 11:22:18 2007 -0500''입니다. Git
	파서는 정확하지만 다소 허용적입니다. 이메일에서 받은 패치를
	적용할 때 'git am'에서 사용하는 것과 동일한 파서입니다.
+
일부 잘못된 형식의 문자열은 유효한 날짜로 허용될 수 있습니다.
	이러한 경우 중 일부에서는 Git이 잘못된 형식의 문자열에서
	정확한 날짜를 얻을 수 있습니다. Git이 잘못 파싱하지만 유효한
	것으로 간주하는 잘못된 형식의 문자열 유형도 있습니다.
	심하게 잘못된 형식의 문자열은 거부됩니다.
+
위 `raw` 형식과 달리, RFC 2822 날짜 문자열에 포함된 시간대/UTC
	오프셋 정보는 저장 전에 날짜 값을 UTC로 조정하는 데 사용됩니다.
	따라서 이 정보가 가능한 한 정확한 것이 중요합니다.
+
소스 자료가 RFC 2822 스타일 날짜를 사용하는 경우,
	Git 파서가 야생에서 잘 테스트되었으므로 프론트엔드는
	(직접 파싱하려고 시도하는 대신) fast-import가 파싱 및
	변환을 처리하도록 해야 합니다.
+
소스 자료가 UNIX 에포크 형식을 이미 사용하거나, 해당 형식으로
	날짜를 제공하도록 유도할 수 있거나, 형식이 쉽게 변환될 수 있는
	경우 프론트엔드는 `raw` 형식을 선호해야 합니다. 파싱에 모호성이
	없기 때문입니다.

`now`::
	항상 현재 시간과 시간대를 사용합니다. `<when>`에 대한 리터럴
	`now`는 항상 제공되어야 합니다.
+
이것은 장난감 형식입니다. 이 시스템의 현재 시간과 시간대는
	fast-import에 의해 생성되는 시점에 항상 ID 문자열에 복사됩니다.
	다른 시간 또는 시간대를 지정하는 방법은 없습니다.
+
이 특정 형식은 구현하기 짧고, 작업 디렉토리나 'git update-index'를
	사용하지 않고 지금 새 커밋을 생성하려는 프로세스에 유용할 수 있기
	때문에 제공됩니다.
+
`commit`에서 별도의 `author` 및 `committer` 명령이 사용되는 경우,
	시스템 시계가 두 번 폴링되므로(각 명령에 대해 한 번) 타임스탬프가
	일치하지 않을 수 있습니다. 작성자와 커미터 정보 모두에 동일한
	타임스탬프가 있도록 하는 유일한 방법은 `author`를 생략하거나
	(따라서 `committer`로부터 복사) `now` 이외의 날짜 형식을 사용하는
	것입니다.

Commands
~~~~~~~~
fast-import는 현재 저장소를 업데이트하고 현재 임포트 프로세스를
제어하기 위해 여러 명령을 받습니다. 각 명령에 대한 자세한 논의
(예제 포함)는 나중에 나옵니다.

`commit`::
	새로운 브랜치를 생성하거나, 새로운 커밋을 생성하고 브랜치를
	새로 생성된 커밋을 가리키도록 업데이트하여 기존 브랜치를 업데이트합니다.

`tag`::
	기존 커밋 또는 브랜치에서 주석 태그 객체를 생성합니다.
	경량 태그는 의미 있는 시점을 기록하는 데 권장되지 않으므로
	이 명령으로는 지원되지 않습니다.

`reset`::
	기존 브랜치(또는 새 브랜치)를 특정 리비전으로 재설정합니다.
	이 명령은 커밋을 만들지 않고 브랜치를 특정 리비전으로 변경하는 데
	사용되어야 합니다.

`blob`::
	`commit` 명령에서 나중에 사용할 원시 파일 데이터를 블롭으로 변환합니다.
	이 명령은 선택 사항이며 임포트를 수행하는 데 필요하지 않습니다.

`alias`::
	새 객체를 먼저 생성하지 않고 mark가 주어진 객체를 참조함을 기록합니다.
	--import-marks를 사용하고 누락된 mark를 참조하면 fast-import가
	실패하므로, alias는 잘린 커밋을 유효한 값(예: 가장 가까운 잘리지 않은
	조상)으로 설정할 방법을 제공할 수 있습니다.

`checkpoint`::
	fast-import가 현재 팩파일을 닫고, 고유한 SHA-1 체크섬 및 인덱스를
	생성하고, 새 팩파일을 시작하도록 강제합니다.
	이 명령은 선택 사항이며 임포트를 수행하는 데 필요하지 않습니다.

`progress`::
	fast-import가 자체 표준 출력으로 전체 줄을 에코하도록 합니다.
	이 명령은 선택 사항이며 임포트를 수행하는 데 필요하지 않습니다.

`done`::
	스트림의 끝을 표시합니다. `done` 기능이 `--done` 명령줄 옵션이나
	`feature done` 명령을 사용하여 요청되지 않은 한 이 명령은 선택 사항입니다.

`get-mark`::
	fast-import가 mark에 해당하는 SHA-1을 `--cat-blob-fd`로 설정된
	파일 디스크립터나, 지정되지 않은 경우 `stdout`에 출력하도록 합니다.

`cat-blob`::
	fast-import가 Blob을 `--cat-blob-fd`로 설정된 파일 디스크립터나,
	지정되지 않은 경우 `stdout`에 'cat-file --batch' 형식으로 출력하도록 합니다.

`ls`::
	fast-import가 `--cat-blob-fd`로 설정된 파일 디스크립터나,
	지정되지 않은 경우 `stdout`에 'ls-tree' 형식으로 디렉토리 항목을
	설명하는 줄을 출력하도록 합니다.

`feature`::
	지정된 기능을 활성화합니다. 이는 fast-import가 해당 기능을
	지원해야 하며, 지원하지 않으면 중단됩니다.

`option`::
	스트림 의미를 변경하지 않고 프론트엔드의 요구에 맞게 OPTIONS 아래에
	나열된 옵션 중 하나를 지정합니다. 이 명령은 선택 사항이며 임포트를
	수행하는 데 필요하지 않습니다.

`commit`
~~~~~~~~
새로운 커밋을 생성하여 브랜치를 생성하거나 업데이트하며, 프로젝트에 대한
하나의 논리적 변경 사항을 기록합니다.

////
네, 'gpgsig' 줄에 후행 `LF`가 없는 것은 의도된 것입니다. `data`의 정의는
바이트 수 접두사를 사용하므로 종결자로 `LF`가 필요하지 않습니다(그리고
`data`에는 원한다면 옵션으로 후행 `LF?`가 이미 포함되어 있습니다).
////

....
	'commit' SP <ref> LF
	mark?
	original-oid?
	('author' (SP <name>)? SP LT <email> GT SP <when> LF)?
	'committer' (SP <name>)? SP LT <email> GT SP <when> LF
	('gpgsig' SP <algo> SP <format> LF data)?
	('encoding' SP <encoding> LF)?
	data
	('from' SP <commit-ish> LF)?
	('merge' SP <commit-ish> LF)*
	(filemodify | filedelete | filecopy | filerename | filedeleteall | notemodify)*
	LF?
....

여기서 `<ref>`는 커밋을 수행할 브랜치의 이름입니다.
일반적으로 Git에서 브랜치 이름은 `refs/heads/`로 접두사가 붙습니다.
CVS 브랜치 심볼 `RELENG-1_0`을 임포트하는 경우 `<ref>`의 값으로
`refs/heads/RELENG-1_0`을 사용합니다. `<ref>`의 값은 Git에서 유효한 refname이어야 합니다.
`LF`는 Git refname에 유효하지 않으므로, 여기서는 따옴표나 이스케이프 구문을 지원하지 않습니다.

`mark` 명령이 선택적으로 나타날 수 있으며, fast-import가 새로 생성된
커밋에 대한 참조를 저장하도록 요청합니다(프론트엔드에서 나중에 사용하기 위해,
아래 형식 참조). 프론트엔드는 생성하는 모든 커밋에 mark를 지정하는 것이
매우 일반적이므로, 모든 임포트된 커밋에서 향후 브랜치 생성이 가능해집니다.

`committer` 뒤의 `data` 명령은 커밋 메시지를 제공해야 합니다(아래 `data`
명령 구문 참조). 빈 커밋 메시지를 임포트하려면 0 길이 데이터를 사용합니다.
커밋 메시지는 자유 형식이며 Git은 해석하지 않습니다. 현재 UTF-8로
인코딩되어야 합니다. fast-import는 다른 인코딩을 지정하는 것을 허용하지 않기
때문입니다.

0개 이상의 `filemodify`, `filedelete`, `filecopy`, `filerename`,
`filedeleteall` 및 `notemodify` 명령이
커밋을 생성하기 전에 브랜치의 내용을 업데이트하기 위해 포함될 수 있습니다.
이 명령들은 어떤 순서로든 제공될 수 있습니다. 그러나 `filedeleteall`은
브랜치를 깨끗하게 지우므로(아래 참조), 동일한 커밋 내에서 다른 모든
`filemodify`, `filecopy`, `filerename` 및 `notemodify` 명령 앞에
`filedeleteall` 명령을 제공하는 것이 좋습니다.

명령 뒤의 `LF`는 선택 사항입니다(이전에는 필수였음).  호환성을 위해,
커밋이 `data` 명령으로 끝나는 경우(즉, `from`, `merge`, `filemodify`,
`filedelete`, `filecopy`, `filerename`, `filedeleteall` 또는
`notemodify` 명령이 없는 경우), 명령 끝에 하나의 `LF` 대신 두 개의
`LF`가 나타날 수 있습니다.

`author`
^^^^^^^^
작성자 정보가 커미터 정보와 다를 수 있는 경우 `author` 명령이 선택적으로
나타날 수 있습니다. `author`가 생략되면 fast-import는 자동으로
커미터의 정보를 커밋의 작성자 부분으로 사용합니다. `author`의 필드 설명은
`committer`와 동일하므로 아래를 참조하십시오.

`committer`
^^^^^^^^^^^
`committer` 명령은 누가 이 커밋을 만들었는지, 그리고 언제 만들었는지
나타냅니다.

여기서 `<name>`은 개인의 표시 이름(예: ``Com M Itter'')이고
`<email>`은 개인의 이메일 주소(``\cm@example.com'')입니다. `LT`와 `GT`는
리터럴 꺽쇠괄호 (\x3c)와 ( \x3e) 기호입니다. 이들은 줄의 다른 필드에서
이메일 주소를 구분하기 위해 필요합니다. `<name>`과 `<email>`은 자유 형식이며
`LT`, `GT`, `LF`를 제외한 모든 바이트 시퀀스를 포함할 수 있습니다. `<name>`은
일반적으로 UTF-8로 인코딩됩니다.

변경 시점은 --date-format=<fmt> 명령줄 옵션으로 선택된 날짜 형식으로
`<when>`을 사용하여 지정됩니다. 지원되는 형식과 구문에 대한 자세한 내용은
위의 ``Date Formats''를 참조하십시오.

`gpgsig`
^^^^^^^^

선택적 `gpgsig` 명령은 커밋 데이터를 서명하는 PGP/GPG 서명 또는 기타
암호화 서명을 포함하는 데 사용됩니다.

....
	'gpgsig' SP <git-hash-algo> SP <signature-format> LF data
....

`gpgsig` 명령은 두 개의 인수를 받습니다.

* `<git-hash-algo>`는 이 서명이 적용되는 Git 객체 형식(sha1 또는 sha256)을
  지정합니다. 이는 어떤 버전의 커밋(SHA-1 또는 SHA-256 버전)이 서명되었는지
  알 수 있게 해주며, 이는 서명 검증 및 다른 해시 함수를 가진 저장소 간의
  상호 운용성에 도움이 됩니다.

* `<signature-format>`은 서명 유형(예: `openpgp`, `x509`, `ssh`, 또는
  `unknown`)을 지정합니다. 이것은 스트림을 처리하는 도구가 ASCII
  아머를 파싱하여 서명 유형을 식별할 필요가 없으므로 편리합니다.

커밋은 SHA-1 객체 형식( "gpgsig" 헤더에 저장됨)에 대해 최대 하나의
서명, 그리고 SHA-256 객체 형식( "gpgsig-sha256" 헤더에 저장됨)에 대해
하나의 서명을 가질 수 있습니다.

서명 데이터의 원시 내용을 포함하는 `data` 명령에 대한 자세한 설명은
아래를 참조하십시오.

아직 현재 구현에서는 서명이 확인되지 않습니다.
(나중에 구현될 때 SHA-1 및 SHA-256 객체 형식 서명을 모두 확인하는 데 도움이
되도록 `extensions.compatObjectFormat` 구성 옵션을 설정해 두는 것이 좋습니다.)

참고: 이것은 매우 실험적이며 `gpgsig` 명령의 형식은 미래에 호환성
보장 없이 변경될 수 있습니다.

`encoding`
^^^^^^^^^^
선택적 `encoding` 명령은 커밋 메시지의 인코딩을 나타냅니다. 대부분의
커밋은 UTF-8이며 인코딩이 생략되지만, 이를 통해 Git에 커밋 메시지를
먼저 재인코딩하지 않고 임포트할 수 있습니다.
