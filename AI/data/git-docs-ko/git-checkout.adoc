git-checkout(1)
===============

NAME
----
git-checkout - 브랜치를 전환하거나 워킹 트리 파일을 복원합니다.

SYNOPSIS
--------
[synopsis]
git checkout [-q] [-f] [-m] [<branch>]
git checkout [-q] [-f] [-m] --detach [<branch>]
git checkout [-q] [-f] [-m] [--detach] <commit>
git checkout [-q] [-f] [-m] [[-b|-B|--orphan] <new-branch>] [<start-point>]
git checkout <tree-ish> [--] <pathspec>...
git checkout <tree-ish> --pathspec-from-file=<file> [--pathspec-file-nul]
git checkout [-f|--ours|--theirs|-m|--conflict=<style>] [--] <pathspec>...
git checkout [-f|--ours|--theirs|-m|--conflict=<style>] --pathspec-from-file=<file> [--pathspec-file-nul]
git checkout (-p|--patch) [<tree-ish>] [--] [<pathspec>...]

DESCRIPTION
-----------

`git checkout`에는 두 가지 주요 모드가 있습니다:

1. **브랜치 전환**, `git checkout <branch>` 사용
2. **파일의 다른 버전 복원**, 예를 들어 `git checkout <commit> <filename>` 또는 `git checkout <filename>` 사용

Git이 어떤 작업을 수행할지 결정하는 방법은 아래의 ARGUMENT DISAMBIGUATION를 참조하십시오.

`git checkout [<branch>]`::
	_<branch>_로 전환합니다. 이는 현재 브랜치를 _<branch>_로 설정하고
	작업 디렉토리의 파일을 업데이트합니다. _<branch>_와 현재 커밋이
	다른 내용을 가진 파일에 커밋되지 않은 변경 사항이 있으면 체크아웃이 실패합니다.
	그렇지 않은 경우, 커밋되지 않은 변경 사항은 유지됩니다.
+
_<branch>_가 존재하지 않지만 정확히 하나의 원격 저장소(이하 _<remote>_)에
	일치하는 이름의 추적 브랜치가 있고 `--no-guess`가 지정되지 않은 경우,
	다음과 같이 처리됩니다.
+
------------
$ git checkout -b <branch> --track <remote>/<branch>
------------
+
브랜치를 지정하지 않고 `git checkout`을 실행하면 현재 브랜치의 추적 정보만
	출력하는 것 외에는 아무런 영향이 없습니다.

`git checkout -b <new-branch> [<start-point>]`::

	_<new-branch>_라는 새 브랜치를 생성하고, _<start-point>_ (기본값은 현재 커밋)에서 시작하여
	새 브랜치를 체크아웃합니다.
	`--track` 또는 `--no-track` 옵션을 사용하여 브랜치의 상위 추적 정보를 설정할 수 있습니다.
+
이것은 _<new-branch>_ 체크아웃 시 오류가 있거나, 예를 들어 `<start-point>` 커밋을
	체크아웃할 때 커밋되지 않은 변경 사항을 덮어쓸 경우 실패합니다.

`git checkout -B <branch> [<start-point>]`::

	`-b`와 동일하지만, 브랜치가 이미 존재하는 경우 실패하는 대신
	_<branch>_를 시작 지점으로 재설정합니다.

`git checkout --detach [<branch>]`::
`git checkout [--detach] <commit>`::

	`git checkout <branch>`와 동일하지만, `HEAD`를 브랜치가 아닌
	커밋 ID를 가리키도록 합니다.
	자세한 내용은 아래의 "DETACHED HEAD" 섹션을 참조하십시오.
+
_<branch>_를 생략하면 현재 브랜치의 끝에서 `HEAD`를 분리합니다.

`git checkout <tree-ish> [--] <pathspec>...`::
`git checkout <tree-ish> --pathspec-from-file=<file> [--pathspec-file-nul]`::

	지정된 파일 및/또는 디렉토리를 주어진 커밋 또는 트리 버전으로
	바꾸고 인덱스("스테이징 영역")에 추가합니다.
+
예를 들어, `git checkout main file.txt`는 `file.txt`를 `main`의 버전으로
	바꿉니다.

`git checkout [-f|--ours|--theirs|-m|--conflict=<style>] [--] <pathspec>...`::
`git checkout [-f|--ours|--theirs|-m|--conflict=<style>] --pathspec-from-file=<file> [--pathspec-file-nul]`::

	지정된 파일 및/또는 디렉토리를 인덱스의 버전으로
	바꿉니다.
+
예를 들어, 커밋을 체크아웃하고 `file.txt`를 수정한 후 해당 변경 사항이
	실수였다고 판단하는 경우, `git checkout file.txt`는 `file.txt`의
	스테이징되지 않은 변경 사항을 삭제합니다.
+
파일에 병합 충돌이 있고 아직 `git add file.txt`(또는 이에 상응하는 것)를
	실행하여 해결된 것으로 표시하지 않은 경우 실패합니다.
	대신 `-f`를 사용하여 병합되지 않은 파일을 무시하거나, `--ours` 또는
	`--theirs`를 사용하여 특정 측의 버전으로 바꾸거나, `-m`을 사용하여
	원래 충돌한 병합 결과로 바꿀 수 있습니다.

`git checkout (-p|--patch) [<tree-ish>] [--] [<pathspec>...]`::
	이전 두 모드와 유사하지만, "diff" 출력을 보여주고 결과를
	어떤 덩어리(hunk)를 사용할지를 선택할 수 있는 대화형 인터페이스를
	사용합니다. `--patch` 옵션에 대한 설명은 아래를 참조하십시오.

OPTIONS
-------
`-q`::
`--quiet`::
	조용히, 피드백 메시지를 억제합니다.

`--progress`::
`--no-progress`::
	진행률 상태는 기본적으로 표준 오류 스트림에 보고되며, 단말기에
	연결되어 있고 `--quiet`가 지정되지 않은 경우입니다. 이 플래그는
	단말기에 연결되어 있지 않아도 진행률 보고를 활성화하며, `--quiet`의
	영향을 받지 않습니다.

`-f`::
`--force`::
	브랜치를 전환할 때, 인덱스나 워킹 트리가 `HEAD`와 다르더라도,
	그리고 추적되지 않는 파일이 방해가 되더라도 계속 진행합니다.
	이는 로컬 변경 사항 및 방해가 되는 추적되지 않는 파일이나
	디렉토리를 모두 버리는 데 사용됩니다.
+
인덱스에서 경로를 체크아웃할 때, 병합되지 않은 항목이 있어도 실패하지
	않습니다. 대신, 병합되지 않은 항목은 무시됩니다.

`--ours`::
`--theirs`::
	인덱스에서 경로를 체크아웃할 때, 병합되지 않은 경로에 대해
	스테이지 #2(`ours`) 또는 #3(`theirs`)를 체크아웃합니다.
+
`git rebase` 및 `git pull --rebase` 중에는 `ours`와 `theirs`가
	바뀌어 보일 수 있습니다. `--ours`는 리베이스되는 브랜치의 버전을 제공하고,
	`--theirs`는 리베이스되는 작업의 버전을 제공합니다.
+
이는 `rebase`가 원격 저장소의 히스토리를 공유된 표준으로 취급하고,
	리베이스되는 브랜치의 작업을 통합할 타사 작업으로 취급하는 워크플로우에서
	사용되기 때문입니다. 리베이스 중에 일시적으로 표준 히스토리의
	유지보수자 역할을 맡게 됩니다. 표준 히스토리의 유지보수자로서
	원격 저장소의 히스토리를 `ours`("우리의 공유된 표준 히스토리")로,
	사이드 브랜치에서 수행한 작업을 `theirs`("그 위에 있는 한 기여자의 작업")로
	봐야 합니다.

`-b <new-branch>`::
	_<new-branch>_라는 새 브랜치를 생성하고, _<start-point>_에
	시작하여 해당 브랜치를 체크아웃합니다. 자세한 내용은
	linkgit:git-branch[1]를 참조하십시오.

`-B <new-branch>`::
	`-b`와 동일하지만, 브랜치가 이미 존재하는 경우 실패하는 대신
	_<branch>_를 시작 지점으로 재설정합니다.

`-t`::
`--track[=(direct|inherit)]`::
	새 브랜치를 생성할 때 "상위" 설정을 구성합니다. 자세한 내용은
	linkgit:git-branch[1]의 `--track`을 참조하십시오. 편의를 위해,
	`-b` 없이 `--track`을 사용하면 브랜치 생성을 의미합니다.
+
`-b` 옵션이 없으면, 새 브랜치의 이름은 원격 추적 브랜치에서 파생됩니다.
	해당 원격 저장소에 대해 구성된 refspec의 로컬 부분을 살펴보고,
	"*"(별표)까지의 시작 부분을 제거합니다.
	이는 `origin/hack`(또는 `remotes/origin/hack`, 심지어
	`refs/remotes/origin/hack`)에서 분기할 때 `hack`을 로컬 브랜치로
	사용하도록 지시합니다. 주어진 이름에 슬래시가 없거나 위의 추측 결과가
	빈 이름이면 추측이 중단됩니다. 이러한 경우 `-b`로 이름을 명시적으로
	지정할 수 있습니다.

`--no-track`::
	`branch.autoSetupMerge` 구성 변수가 true이더라도 "상위" 구성을
	설정하지 않습니다.

`--guess`::
`--no-guess`::
	_<branch>_가 존재하지 않지만 정확히 하나의 원격 저장소(이하 _<remote>_)에
	일치하는 이름의 추적 브랜치가 있는 경우, 다음을 처리하는 것과
	동일하게 취급합니다.
+
------------
$ git checkout -b <branch> --track <remote>/<branch>
------------
+
브랜치가 여러 원격 저장소에 존재하고 그중 하나가 `checkout.defaultRemote`
	구성 변수에 의해 명명된 경우, _<branch>_가 모든 원격 저장소에 걸쳐
	고유하지 않더라도 모호성을 해소하기 위해 해당 원격 저장소를 사용합니다.
	예를 들어 `checkout.defaultRemote=origin`으로 설정하면 _<branch>_가
	모호하더라도 'origin' 원격 저장소에 있으면 항상 거기서 원격 브랜치를
	체크아웃합니다. `checkout.defaultRemote`는 linkgit:git-config[1]에서도
	확인할 수 있습니다.
+
`--guess`가 기본 동작입니다. 비활성화하려면 `--no-guess`를 사용하십시오.
+
기본 동작은 `checkout.guess` 구성 변수를 통해 설정할 수 있습니다.

`-l`::
	새 브랜치의 reflog를 생성합니다. 자세한 내용은
	linkgit:git-branch[1]를 참조하십시오.

`-d`::
`--detach`::
	작업할 브랜치를 체크아웃하는 대신, 검사 및 폐기 가능한 실험을
	위해 커밋을 체크아웃합니다.
	이것은 _<commit>_이 브랜치 이름이 아닐 때 `git checkout <commit>`의
	기본 동작입니다. 자세한 내용은 아래의 "DETACHED HEAD" 섹션을 참조하십시오.

`--orphan <new-branch>`::
	_<new-branch>_라는 새 태어나지 않은 브랜치를 생성하고, _<start-point>_에서
	시작하여 해당 브랜치로 전환합니다. 이 새 브랜치에서 작성된 첫
	번째 커밋은 부모가 없으며, 다른 모든 브랜치와 커밋에서 완전히
	분리된 새 히스토리의 루트가 됩니다.
+
인덱스와 워킹 트리는 이전에 `git checkout <start-point>`를 실행한 것처럼
	조정됩니다. 이를 통해 `git commit -a`를 쉽게 실행하여 루트 커밋을
	만들고 _<start-point>_와 유사한 경로 집합을 기록하는 새 히스토리를
	시작할 수 있습니다.
+
이는 전체 히스토리를 노출하지 않고 커밋의 트리를 게시하고 싶을 때 유용합니다.
	예를 들어, 프로젝트의 오픈 소스 브랜치를 게시하려는 경우 현재 트리가
	"깨끗"하지만 전체 히스토리에 독점적이거나 기타 제약이 있는 코드 조각이
	포함되어 있을 수 있습니다.
+
_<start-point>_와 완전히 다른 경로 집합을 기록하는 분리된 히스토리를
	시작하고 싶다면, orphan 브랜치를 생성한 직후 워킹 트리의 최상위 레벨에서
	`git rm -rf .`를 실행하여 인덱스와 워킹 트리를 지워야 합니다.
	그 후, 다른 곳에서 복사하거나, tarball을 추출하는 등의 방법으로
	파일을 준비하여 워킹 트리를 다시 채울 준비가 됩니다.

`--ignore-skip-worktree-bits`::
	스파스 체크아웃 모드에서 `git checkout -- <path>...`는 _<path>_와
	`$GIT_DIR/info/sparse-checkout`의 스파스 패턴에 일치하는 항목만
	업데이트합니다. 이 옵션은 스파스 패턴을 무시하고 `<path>...`의
	파일을 다시 추가합니다.

`-m`::
`--merge`::
	브랜치를 전환할 때, 현재 브랜치와 전환하려는 브랜치 간에
	내용이 다른 하나 이상의 파일에 대한 로컬 수정 사항이 있는 경우,
	명령은 수정 사항을 컨텍스트에서 보존하기 위해 브랜치 전환을
	거부합니다. 이 옵션을 사용하면 충돌하는 로컬 변경 사항이
	전환 전에 자동으로 스태시되고 이후에 다시 적용됩니다.
+
로컬 변경 사항이 브랜치 간의 차이점과 겹치지 않으면, 스태시 없이 전환이
	진행됩니다. 스태시를 다시 적용할 때 충돌이 발생하면 해당 항목은
	스태시 목록에 저장됩니다. 완료 후 충돌을 해결하고 `git stash drop`을
	실행하거나, 나중에 `git stash pop`를 실행하여 변경 사항을 다시
	적용하기 전에 작업 트리를 지웁니다(예: `git reset --hard` 사용).
+
인덱스에서 경로를 체크아웃할 때, 이 옵션을 사용하면 지정된 경로에서
	충돌한 병합을 다시 생성할 수 있습니다. 이 옵션은 tree-ish에서
	경로를 체크아웃할 때는 사용할 수 없습니다.

`--conflict=<style>`::
	`--merge` 옵션과 동일하지만, 충돌하는 덩어리(hunk)가 표시되는
	방식을 변경하고 `merge.conflictStyle` 구성 변수를 재정의합니다.
	가능한 값은 `merge`(기본값), `diff3`, `zdiff3`입니다.

`-p`::
`--patch`::
	_<tree-ish>_ (또는 지정되지 않은 경우 인덱스)와 워킹 트리 간의
	차이점에서 덩어리(hunk)를 대화식으로 선택합니다. 선택된 덩어리는
	워킹 트리에 역으로 적용됩니다(그리고 _<tree-ish>_가 지정된 경우 인덱스에도).
+
이것은 `git checkout -p`를 사용하여 현재 워킹 트리의 편집 내용을
	선택적으로 삭제할 수 있음을 의미합니다. `--patch` 모드를 작동시키는
	방법은 linkgit:git-add[1]의 "Interactive Mode" 섹션을 참조하십시오.
+
이 옵션은 기본적으로 non-overlay 모드를 사용하며(또한 `--overlay` 참조),
	overlay 모드는 현재 지원하지 않습니다.

`--ignore-other-worktrees`::
	`git checkout`은 원하는 브랜치가 이미 체크아웃되었거나 다른
	worktree에서 사용 중인 경우 실패합니다. 이 옵션을 사용하면
	어쨌든 해당 브랜치를 체크아웃합니다. 즉, 브랜치가 여러 worktree에서
	사용될 수 있습니다.

`--overwrite-ignore`::
`--no-overwrite-ignore`::
	브랜치를 전환할 때 무시된 파일을 조용히 덮어씁니다. 이것이
	기본 동작입니다. 새 브랜치에 무시된 파일이 포함될 때 작업을
	중단하려면 `--no-overwrite-ignore`를 사용하십시오.

`--recurse-submodules`::
`--no-recurse-submodules`::
	`--recurse-submodules`를 사용하면 슈퍼프로젝트에 기록된 커밋에
	따라 모든 활성 하위 모듈의 내용이 업데이트됩니다. 하위 모듈의
	로컬 수정 사항이 덮어쓰여 체크아웃이 실패할 경우 `-f`를 사용하지
	않으면 실패합니다. 아무것도 사용하지 않거나 (`--no-recurse-submodules`)
	사용하면 하위 모듈 워킹 트리도 업데이트되지 않습니다.
	linkgit:git-submodule[1]과 마찬가지로, 이는 하위 모듈의 `HEAD`를
	분리합니다.

`--overlay`::
`--no-overlay`::
	기본 overlay 모드에서는 `git checkout`이 인덱스나 워킹 트리에서
	파일을 제거하지 않습니다. `--no-overlay`를 지정하면, 인덱스와
	워킹 트리에 있으면서 _<tree-ish>_에는 없는 파일이 제거되어
	_<tree-ish>_와 완전히 일치하도록 합니다.

`--pathspec-from-file=<file>`::
	pathspec은 명령줄 인수 대신 _<file>_에서 전달됩니다. _<file>_이
	정확히 `-`이면 표준 입력이 사용됩니다. Pathspec 요소는 _LF_ 또는
	_CR_/_LF_로 구분됩니다. Pathspec 요소는 `core.quotePath` 구성
	변수에 대한 설명(linkgit:git-config[1] 참조)에 따라 따옴표로 묶을 수
	있습니다. `--pathspec-file-nul` 및 전역 `--literal-pathspecs`도
	참조하십시오.

`--pathspec-file-nul`::
	`--pathspec-from-file`만 유효합니다. Pathspec 요소는 _NUL_ 문자로
	구분되며 다른 모든 문자는 문자 그대로 처리됩니다(줄 바꿈 및 따옴표
	포함).

`<branch>`::
	체크아웃할 브랜치. 만약 브랜치(즉, "refs/heads/"가 앞에 붙었을 때
	유효한 ref인 이름)를 참조하면 해당 브랜치가 체크아웃됩니다.
	그렇지 않고 유효한 커밋을 참조하면, `HEAD`가 "분리"되어 더 이상
	어떤 브랜치에도 속하지 않게 됩니다(자세한 내용은 아래 참조).
+
`@{-N}` 구문을 사용하여 "git checkout" 작업을 통해 마지막으로 체크아웃한
	N번째 브랜치/커밋을 참조할 수 있습니다. `-`를 사용하여 `@{-1}`과
	동일하게 사용할 수도 있습니다.
+
특별한 경우로, _<rev-a>_와 _<rev-b>_ 사이에 정확히 하나의 병합 기반이
	있는 경우 `<rev-a>...<rev-b>`를 병합 기반의 바로 가기로 사용할 수 있습니다.
	_<rev-a>_와 _<rev-b>_ 중 하나를 비워둘 수 있으며, 이 경우 `HEAD`가
	기본값으로 사용됩니다.

_<new-branch>_::
	새 브랜치의 이름.

_<start-point>_::
	새 브랜치를 시작할 커밋의 이름. 자세한 내용은
	linkgit:git-branch[1]를 참조하십시오. 기본값은 `HEAD`입니다.
+
특별한 경우로, _<rev-a>_와 _<rev-b>_ 사이에 정확히 하나의 병합 기반이
	있는 경우 `<rev-a>...<rev-b>`를 병합 기반의 바로 가기로 사용할 수 있습니다.
	_<rev-a>_와 _<rev-b>_ 중 하나를 비워둘 수 있으며, 이 경우 `HEAD`가
	기본값으로 사용됩니다.

_<tree-ish>_::
	체크아웃할 트리(경로를 지정할 때). 지정하지 않으면 인덱스가
	사용됩니다.
+
특별한 경우로, _<rev-a>_와 _<rev-b>_ 사이에 정확히 하나의 병합 기반이
	있는 경우 `<rev-a>...<rev-b>`를 병합 기반의 바로 가기로 사용할 수 있습니다.
	_<rev-a>_와 _<rev-b>_ 중 하나를 비워둘 수 있으며, 이 경우 `HEAD`가
	기본값으로 사용됩니다.

`--`::
	이후의 인수를 옵션으로 해석하지 않습니다.

`<pathspec>...`::
	연산에 영향을 받는 경로를 제한합니다.
+
자세한 내용은 linkgit:gitglossary[7]의 'pathspec' 항목을 참조하십시오.

DETACHED HEAD
-------------
`HEAD`는 일반적으로 명명된 브랜치(예: `master`)를 참조합니다. 동시에 각
브랜치는 특정 커밋을 참조합니다. 세 개의 커밋이 있는 저장소를 살펴보고,
그중 하나에 태그가 붙어 있으며, `master` 브랜치가 체크아웃된 상태를
살펴보겠습니다.

------------
           HEAD (브랜치 'master' 참조)
            |
            v
a---b---c  브랜치 'master' (커밋 'c' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

이 상태에서 커밋을 생성하면, 브랜치가 새 커밋을 참조하도록 업데이트됩니다.
구체적으로, `git commit`은 커밋 `c`를 부모로 하는 새 커밋 `d`를 생성하고,
이어서 브랜치 `master`를 새 커밋 `d`를 참조하도록 업데이트합니다. `HEAD`는
여전히 브랜치 `master`를 참조하며, 따라서 간접적으로 커밋 `d`를
참조합니다.

------------
$edit; git add; git commit

               HEAD (브랜치 'master' 참조)
                |
                v
a---b---c---d  브랜치 'master' (커밋 'd' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

이름이 지정된 브랜치의 끝에 있지 않은 커밋을 체크아웃하거나, 이름이
지정된 브랜치로 참조되지 않는 새 커밋을 만드는 것이 때때로 유용할 수 있습니다.
커밋 `b`를 체크아웃할 때 무슨 일이 일어나는지 살펴봅시다(여기서는 두 가지
방법을 보여줍니다).

------------
$ git checkout v2.0  # 또는
$ git checkout master^^

   HEAD (커밋 'b' 참조)
    |
    v
a---b---c---d  브랜치 'master' (커밋 'd' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

어떤 checkout 명령을 사용하든 `HEAD`가 이제 커밋 `b`를 직접 참조하는 것을
볼 수 있습니다. 이것을 분리된 `HEAD` 상태라고 합니다.
단순히 `HEAD`가 명명된 브랜치가 아닌 특정 커밋을 참조한다는 것을 의미합니다.
커밋을 만들 때 무슨 일이 일어나는지 살펴봅시다.

------------
$ edit; git add; git commit

     HEAD (커밋 'e' 참조)
      |
      v
      e
     /
a---b---c---d  브랜치 'master' (커밋 'd' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

이제 새 커밋 `e`가 생겼지만, `HEAD`만 참조하고 있습니다. 이 상태에서
물론 또 다른 커밋을 수행할 수도 있습니다.

------------
$ edit; git add; git commit

	 HEAD (커밋 'f' 참조)
	  |
	  v
      e---f
     /
a---b---c---d  브랜치 'master' (커밋 'd' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

실제로 모든 일반 Git 작업을 수행할 수 있습니다. 하지만 `master`를
체크아웃할 때 무슨 일이 일어나는지 살펴봅시다.

------------
$ git checkout master

               HEAD (브랜치 'master' 참조)
      e---f     |
     /          v
a---b---c---d  브랜치 'master' (커밋 'd' 참조)
    ^
    |
  tag 'v2.0' (커밋 'b' 참조)
------------

이 시점에서 커밋 `f`를 참조하는 것이 아무것도 없다는 것을 인지하는 것이
중요합니다. 커밋 `f`(및 이를 확장하여 커밋 `e`)는 루틴 Git 가비지
수집 프로세스에 의해 삭제될 것입니다. 그 전에 참조를 생성하지 않으면
그렇습니다. 아직 커밋 `f`에서 벗어나지 않았다면, 다음 중 여기서 참조를
생성할 수 있습니다.

------------
$ git checkout -b foo  # 또는 "git switch -c foo"  <1>
$ git branch foo                                 <2>
$ git tag foo                                    <3>
------------
<1> 새 브랜치 `foo`를 생성하고, 이것이 커밋 `f`를 참조하도록 하고,
    그 후 `HEAD`를 브랜치 `foo`를 참조하도록 업데이트합니다. 즉,
    이 명령 이후에는 더 이상 분리된 `HEAD` 상태가 아닙니다.
<2> 마찬가지로 새 브랜치 `foo`를 생성하고, 이것이 커밋 `f`를 참조하도록
    하지만 `HEAD`는 분리된 상태로 둡니다.
<3> 새 태그 `foo`를 생성하고, 이것이 커밋 `f`를 참조하도록 하여
    `HEAD`를 분리된 상태로 둡니다.

커밋 `f`에서 벗어났다면, 먼저 해당 객체 이름을 복구해야 합니다(일반적으로
git reflog 사용). 그런 다음 해당 객체에 대한 참조를 생성할 수 있습니다.
예를 들어, `HEAD`가 마지막으로 참조했던 두 커밋을 보려면 다음 명령 중
하나를 사용할 수 있습니다.

------------
$ git reflog -2 HEAD # 또는
$ git log -g -2 HEAD
------------

ARGUMENT DISAMBIGUATION
-----------------------

`git checkout <something>`을 실행할 때, Git은 _<something>_이
브랜치, 커밋 또는 파일 집합을 의도하는지 추측하려고 시도한 다음,
해당 브랜치나 커밋으로 전환하거나 지정된 파일을 복원합니다.

모호성이 있는 경우, Git은 `<something>`을 브랜치나 커밋으로 취급하지만,
이중 대시 `--`를 사용하여 Git이 매개변수를 파일 및/또는 디렉토리 목록으로
강제로 취급하도록 할 수 있습니다. 예:

----------
git checkout -- file.txt
----------

EXAMPLES
--------

=== 1. Paths

다음 시퀀스는 `master` 브랜치를 체크아웃하고, `Makefile`을 두 리비전
이전으로 되돌리고, `hello.c`를 실수로 삭제한 다음, 인덱스에서 다시
가져옵니다.

------------
$ git checkout master             <1>
$ git checkout master~2 Makefile  <2>
$ rm -f hello.c
$ git checkout hello.c            <3>
------------
<1> 브랜치 전환
<2> 다른 커밋에서 파일을 가져옵니다.
<3> `hello.c`를 인덱스에서 복원합니다.

모든 C 소스 파일을 인덱스에서 체크아웃하려면 다음과 같이 할 수 있습니다.

------------
$ git checkout -- '*.c'
------------

`*.c` 주변의 따옴표에 유의하십시오. 파일 `hello.c`도 체크아웃됩니다.
작업 트리에는 더 이상 없더라도, 파일 globbing이 쉘이 아닌
인덱스 항목과 일치하는 데 사용되기 때문입니다.

`hello.c`라는 불행한 브랜치가 있다면, 이 단계는 해당 브랜치로
전환하라는 명령으로 혼동될 수 있습니다. 대신 이렇게 작성해야 합니다.

------------
$ git checkout -- hello.c
------------

=== 2. Merge

잘못된 브랜치에서 작업한 후, 올바른 브랜치로 전환하려면 다음과 같이
합니다.

------------
$ git checkout mytopic
------------

그러나 "잘못된" 브랜치와 올바른 `mytopic` 브랜치는 로컬에서 수정된
파일에서 다를 수 있습니다. 이 경우 위의 체크아웃은 다음과 같이 실패합니다.

------------
$ git checkout mytopic
error: You have local changes to 'frotz'; not switching branches.
------------

명령에 `-m` 플래그를 제공하면 로컬 변경 사항이 새 브랜치로
전달됩니다.

------------
$ git checkout -m mytopic
Applied autostash.
Switched to branch 'mytopic'
The following paths have local changes:
M	frotz
------------

전환 후 로컬 수정 사항이 다시 적용되며 인덱스 파일에 등록되지
않습니다. 따라서 `git diff`는 새 브랜치의 끝 부분부터 어떤
변경 사항을 만들었는지 보여줍니다.

=== 3. Merge conflict

`--merge` (`-m`) 옵션이 제공되고 로컬 변경 사항이 전환하려는 브랜치의
변경 사항과 겹칠 때, 변경 사항이 스태시되고 전환 후 다시 적용됩니다.
이 프로세스가 충돌을 발생시키면 스태시 항목이 저장되고 메시지가
인쇄됩니다.

------------
$ git checkout -m mytopic
Your local changes are stashed, however applying them
resulted in conflicts.  You can either resolve the conflicts
and then discard the stash with "git stash drop", or, if you
do not want to resolve them now, run "git reset --hard" and
apply the local changes later by running "git stash pop".
------------
