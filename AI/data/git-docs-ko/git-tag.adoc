git-tag(1)
==========

NAME
----
git-tag - Create, list, delete or verify tags


SYNOPSIS
--------
[synopsis]
git tag [-a | -s | -u <key-id>] [-f] [-m <msg> | -F <file>] [-e]
	[(--trailer <token>[(=|:)<value>])...]
	<tagname> [<commit> | <object>]
git tag -d <tagname>...
git tag [-n[<num>]] -l [--contains <commit>] [--no-contains <commit>]
	[--points-at <object>] [--column[=<options>] | --no-column]
	[--create-reflog] [--sort=<key>] [--format=<format>]
	[--merged <commit>] [--no-merged <commit>] [<pattern>...]
git tag -v [--format=<format>] <tagname>...

DESCRIPTION
-----------

`refs/tags/`에 태그 참조를 추가합니다. `-d`/`-l`/`-v`가 주어지면 태그를 삭제, 나열 또는 검증합니다.

`-f`가 주어지지 않으면, 지정된 이름의 태그는 아직 존재하지 않아야 합니다.

`-a`, `-s`, 또는 `-u <key-id>`가 전달되면, `git tag`는 'tag' 객체를 생성하고 태그 메시지를 필요로 합니다. `-m <msg>` 또는 `-F <file>`이 주어지지 않으면, 사용자에게 태그 메시지를 입력받기 위해 에디터가 시작됩니다.

`-m <msg>` 또는 `-F <file>` 또는 `--trailer <token>[=<value>]`가 주어지고 `-a`, `-s`, `-u <key-id>`가 없을 경우, `-a`가 암시됩니다.

그렇지 않으면, 주어진 객체를 직접 가리키는 태그 참조(즉, 경량 태그)가 생성됩니다.

암호학적으로 서명된 태그 객체는 `-s` 또는 `-u <key-id>`를 사용할 때 생성됩니다. 서명 백엔드(GPG, X.509, SSH 등)는 `gpg.format` 구성 변수에 의해 제어되며, 기본값은 OpenPGP입니다. `-u <key-id>`가 사용되지 않으면, 현재 사용자의 커미터 신원이 서명 키를 찾는 데 사용됩니다. `gpg.program` 구성 변수는 사용자 정의 서명 바이너리를 지정하는 데 사용됩니다.

태그 객체 (`-a`, `-s`, 또는 `-u`로 생성됨)는 "annotated" 태그라고 합니다. 이들은 생성 날짜, 태거 이름 및 이메일, 태그 메시지, 선택적 암호학적 서명을 포함합니다. 반면, "lightweight" 태그는 객체(일반적으로 커밋 객체)에 대한 이름일 뿐입니다.

Annotated 태그는 릴리스를 위한 것이고 lightweight 태그는 비공개 또는 임시 객체 레이블을 위한 것입니다. 이러한 이유로, 객체 명명에 대한 일부 `git` 명령 (`git describe`와 같은)은 기본적으로 lightweight 태그를 무시합니다.


OPTIONS
-------
`-a`::
`--annotate`::
	서명되지 않은, annotated 태그 객체를 만듭니다.

`-s`::
`--sign`::
	기본 서명 키를 사용하여 암호학적으로 서명된 태그를 만듭니다. 사용되는 서명 백엔드는 `gpg.format` 구성 변수에 따라 달라집니다. 기본 키는 백엔드에 의해 결정됩니다. GPG의 경우 커미터의 이메일 주소를 기반으로 하며, SSH의 경우 특정 키 파일 또는 에이전트 신원일 수 있습니다. linkgit:git-config[1]을 참조하십시오.

`--no-sign`::
	각각의 모든 태그가 서명되도록 강제하는 `tag.gpgSign` 구성 변수를 재정의합니다.

`-u <key-id>`::
`--local-user=<key-id>`::
	지정된 키를 사용하여 암호학적으로 서명된 태그를 만듭니다. `<key-id>`의 형식과 사용되는 백엔드는 `gpg.format` 구성 변수에 따라 달라집니다. linkgit:git-config[1]을 참조하십시오.

`-f`::
`--force`::
	기존 태그를 해당 이름으로 바꿉니다 (실패하는 대신).

`-d`::
`--delete`::
	지정된 이름의 기존 태그를 삭제합니다.

`-v`::
`--verify`::
	지정된 태그의 암호학적 서명을 검증합니다.

`-n<num>`::
	`_`num_`은 `-l`을 사용할 때 주석에서 출력할 줄 수를 지정합니다. `--list`를 암시합니다.
+
기본값은 주석 줄을 출력하지 않는 것입니다.
`-n`에 숫자가 지정되지 않으면 첫 번째 줄만 출력됩니다.
태그가 annotated가 아니면 커밋 메시지가 대신 표시됩니다.

`-l`::
`--list`::
	태그를 나열합니다. 선택적 `<pattern>...`과 함께 사용하면 (예: `git tag --list 'v-*'`), 패턴과 일치하는 태그만 나열됩니다.
+
인수 없이 `git tag`를 실행해도 모든 태그가 나열됩니다. 패턴은 셸 와일드카드입니다 (`fnmatch`(3)를 사용하여 일치). 여러 패턴을 지정할 수 있으며, 그중 하나라도 일치하면 해당 태그가 표시됩니다.
+
`--contains`와 같이 다른 목록 관련 옵션이 제공되면 이 옵션은 암묵적으로 공급됩니다. 자세한 내용은 각 옵션의 문서를 참조하십시오.

`--sort=<key>`::
	지정된 키를 기준으로 정렬합니다. `_`-_` 접두사는 해당 값의 내림차순으로 정렬합니다. `--sort=<key>` 옵션을 여러 번 사용할 수 있으며, 이 경우 마지막 _<key>_가 주 키가 됩니다. 또한 "`version:refname`" 또는 "`v:refname`" (태그 이름은 버전으로 처리됨)를 지원합니다. "`version:refname`" 정렬 순서는 "`versionsort.suffix`" 구성 변수에 의해 영향을 받을 수도 있습니다.
	지원되는 키는 `git for-each-ref`와 동일합니다.
	정렬 순서는 `tag.sort` 변수에 구성된 값이 있거나 없으면 사전순서대로 기본 설정됩니다. linkgit:git-config[1]을 참조하십시오.

`--color[=<when>]`::
	`--format` 옵션에 지정된 색상을 존중합니다. `<when>` 필드는 `always`, `never`, 또는 `auto` 중 하나여야 합니다 (`<when>`이 없으면 `always`가 주어진 것처럼 동작합니다).

`-i`::
`--ignore-case`::
	태그를 정렬하고 필터링할 때 대소문자를 구분하지 않습니다.

`--omit-empty`::
	형식이 빈 문자열로 확장되는 형식화된 ref 뒤에 줄 바꿈을 출력하지 않습니다.

`--column[=<options>]`::
`--no-column`::
	태그 목록을 열로 표시합니다. `column.tag` 구성 변수에서 옵션 구문을 참조하십시오. 옵션 없이 `--column` 및 `--no-column`은 각각 `always` 및 `never`와 동일합니다.
+
이 옵션은 주석 줄 없이 태그를 나열할 때만 적용됩니다.

`--contains [<commit>]`::
	_<commit>_ (지정되지 않은 경우 `HEAD`)을 포함하는 태그만 나열합니다. `--list`를 암시합니다.

`--no-contains [<commit>]`::
	_<commit>_ (지정되지 않은 경우 `HEAD`)을 포함하지 않는 태그만 나열합니다. `--list`를 암시합니다.

`--merged [<commit>]`::
	_<commit>_ (지정되지 않은 경우 `HEAD`)에서 도달 가능한 커밋을 가진 태그만 나열합니다.

`--no-merged [<commit>]`::
	_<commit>_ (지정되지 않은 경우 `HEAD`)에서 도달할 수 없는 커밋을 가진 태그만 나열합니다.

`--points-at [<object>]`::
	_<object>_ (지정되지 않은 경우 `HEAD`)의 태그만 나열합니다. `--list`를 암시합니다.

`-m <msg>`::
`--message=<msg>`::
	_`<msg>`_를 사용합니다 (프롬프트를 대신하여).
	여러 `-m` 옵션이 주어지면, 해당 값들이 별개의 단락으로 연결됩니다.
	`-a`, `-s`, 또는 `-u <key-id>` 중 어느 것도 주어지지 않으면 `-a`를 암시합니다.

`-F <file>`::
`--file=<file>`::
	태그 메시지를 _<file>_에서 가져옵니다. `-`를 사용하여 표준 입력에서 메시지를 읽습니다.
	`-a`, `-s`, 또는 `-u <key-id>` 중 어느 것도 주어지지 않으면 `-a`를 암시합니다.

`--trailer <token>[(=|:)<value>]`::
	트레일러로 적용될 (_<token>_, _<value>_) 쌍을 지정합니다. (예: `git tag --trailer "Custom-Key: value"`는 태그 메시지에 "Custom-Key" 트레일러를 추가합니다.)
	`trailer.*` 구성 변수(linkgit:git-interpret-trailers[1])는 중복된 트레일러가 생략되는지, 각 트레일러가 어떤 순서로 나타나는지, 그리고 다른 세부 정보를 정의하는 데 사용될 수 있습니다.
	트레일러는 `git tag --list`에서 `--(format="%(trailers)")` 플레이스홀더를 사용하여 추출할 수 있습니다.

`-e`::
`--edit`::
	`-F`에서 가져온 파일 및 `-m`으로 가져온 명령줄 메시지를 추가로 편집합니다.

`--cleanup=<mode>`::
	태그 메시지가 정리되는 방식을 설정합니다.
	_<mode>_는 `verbatim`, `whitespace`, `strip` 중 하나가 될 수 있습니다. `strip` 모드가 기본값입니다. `verbatim` 모드는 메시지를 전혀 변경하지 않고, `whitespace`는 선행/후행 공백 줄만 제거하며, `strip`은 공백과 주석을 모두 제거합니다.

`--create-reflog`::
	태그에 대한 reflog를 생성합니다. 태그에 대한 reflog를 전역적으로 활성화하려면 linkgit:git-config[1]의 `core.logAllRefUpdates`를 참조하십시오.
	부정 형태인 `--no-create-reflog`는 이전 `--create-reflog`만 재정의하며, 현재 `core.logAllRefUpdates` 설정을 부정하지는 않습니다.

`--format=<format>`::
	표시되는 태그 ref와 그것이 가리키는 객체에서 `%(fieldname)`를 보간하는 문자열입니다. 형식은 linkgit:git-for-each-ref[1]의 형식과 동일합니다. 지정되지 않으면 `%(refname:strip=2)`로 기본 설정됩니다.

_<tagname>_::
	생성, 삭제 또는 설명할 태그의 이름입니다.
	새로운 태그 이름은 linkgit:git-check-ref-format[1]에 정의된 모든 검사를 통과해야 합니다. 이러한 검사 중 일부는 태그 이름에서 허용되는 문자를 제한할 수 있습니다.

_<commit>_::
_<object>_::
	새로운 태그가 참조할 객체, 보통 커밋입니다.
	`HEAD`로 기본 설정됩니다.

CONFIGURATION
-------------
기본적으로, `-s` (sign-with-default 모드)의 `git tag`는 커미터 신원 (`Your Name <your@email.address>` 형식)을 사용하여 키를 찾습니다. 다른 기본 키를 사용하려면 저장소 구성에 다음과 같이 지정할 수 있습니다.

-------------------------------------
[user]
	signingKey = <key-id>
-------------------------------------

서명 백엔드는 `gpg.format` 구성 변수를 통해 선택할 수 있으며, 기본값은 `openpgp`입니다. 지원되는 다른 형식 목록은 linkgit:git-config[1]을 참조하십시오.

각 서명 백엔드에 사용되는 프로그램 경로는 `gpg.<format>.program` 구성 변수로 지정할 수 있습니다. `openpgp` 백엔드의 경우 `gpg.program`은 `gpg.openpgp.program`의 동의어로 사용할 수 있습니다. 자세한 내용은 linkgit:git-config[1]을 참조하십시오.

`pager.tag`는 태그를 나열할 때만 존중됩니다 (`-l`이 사용되거나 암시될 때). 기본값은 페이지어를 사용하는 것입니다.

자세한 내용과 다른 구성 변수는 linkgit:git-config[1]을 참조하십시오.

DISCUSSION
----------

Re-tagging에 대하여
~~~~~~~~~~~~~~~~~~~~~

잘못된 커밋을 태그했고 다시 태그하고 싶을 때 어떻게 해야 할까요?

아무것도 푸시하지 않았다면, 그냥 다시 태그하십시오. `-f`를 사용하여 이전 것을 바꿉니다. 그러면 끝입니다.

하지만 푸시했거나 (또는 다른 사람들이 저장소를 직접 읽을 수 있는 경우), 다른 사람들은 이미 이전 태그를 보았을 것입니다. 이 경우 두 가지 방법 중 하나를 수행할 수 있습니다.

1. 현명한 방법.
   문제가 있었음을 인정하고 다른 이름을 사용하십시오. 다른 사람들은 이미 태그 이름 하나를 보았고, 같은 이름을 사용하면 "버전 X"를 가진 두 사람이 실제로 '다른' "X"를 갖게 되는 상황에 처할 수 있습니다. 따라서 그냥 "X.1"이라고 부르고 끝내십시오.

2. 어리석은 방법.
   다른 사람들이 이미 이전 태그를 보았음에도 불구하고 새 버전을 "X"라고 부르고 싶습니다. 이 경우, 마치 이전 것을 게시한 적이 없는 것처럼 `git tag -f`를 다시 사용하십시오.

그러나 Git은 사용자의 뒤에서 태그를 변경하지 않으며 (그리고 하지 말아야 합니다). 따라서 누군가 이미 이전 태그를 가지고 있다면, 당신의 트리를 `git pull`해도 이전 태그가 덮어쓰여지지 않습니다.

릴리스 태그를 당신으로부터 받은 경우, 당신 자신의 태그를 업데이트하는 것만으로 그들을 위해 태그를 변경할 수 없습니다. 이것은 큰 보안 문제입니다. 사람들은 자신의 태그 이름을 신뢰할 수 있어야 하기 때문입니다. 당신이 정말로 미친 짓을 하려면, 그냥 솔직하게 말하고 사람들이 당신이 실수를 했다고 알릴 필요가 있습니다. 다음을 수행하여 공개적으로 발표해야 합니다.

------------
네, 제가 실수를 해서 X로 태그된 이전 버전을 푸시했습니다. 그런 다음 무언가를 수정했고 *수정된* 트리를 다시 X로 태그했습니다.

잘못된 태그를 받았고 새 태그를 원하면, 이전 태그를 삭제하고 다음을 수행하여 새 태그를 가져오십시오:

	git tag -d X
	git fetch origin tag X

제 업데이트된 태그를 가져오려면.

다음과 같이 수행하여 어떤 태그를 가지고 있는지 테스트할 수 있습니다.

	git rev-parse X

새 버전을 가지고 있다면 0123456789abcdef..를 반환해야 합니다.

번거롭게 해드려 죄송합니다.
------------

이것이 좀 복잡하게 보이나요? 복잡해야 합니다. 자동화된 방식으로 "수정"하는 것이 올바른 방법은 없습니다. 사람들은 자신의 태그가 변경될 수 있다는 것을 알아야 합니다.


Automatic following에 대하여
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

다른 사람의 트리를 따라가고 있다면, 아마도 원격 추적 브랜치(예: `refs/remotes/origin/master`)를 사용하고 있을 것입니다. 다른 쪽의 태그를 얻고 싶을 것입니다.

반면에, 일회성 머지를 원해서 가져오고 있다면, 보통 거기서 태그를 얻고 싶지 않을 것입니다. 이는 최상위 레벨에 있는 사람들에게 더 자주 발생하지만, 그들에 국한되지는 않습니다. 서로간에 풀링하는 일반 사람들은 다른 사람의 비공개 앵커 포인트 태그를 자동으로 얻고 싶어하지 않습니다.

종종 메일링 리스트의 "please pull" 메시지는 저장소 URL과 브랜치 이름, 두 가지 정보만 제공합니다. 이는 `git fetch` 명령줄 끝에 쉽게 복사하여 붙여넣을 수 있도록 설계되었습니다:

------------
Linus, please pull from

	git://git..../proj.git master

to get the following updates...
------------

다음과 같이 됩니다:

------------
$ git pull git://git..../proj.git master
------------

이런 경우, 다른 사람의 태그를 자동으로 따라가고 싶지 않을 것입니다.

Git의 중요한 측면 중 하나는 분산된 특성이며, 이는 시스템에 내재적인 "업스트림" 또는 "다운스트림"이 없다는 것을 의미합니다. 표면적으로 볼 때 위의 예는 태그 네임스페이스가 사람들의 최상위 계층에 의해 소유되고 태그가 아래로만 흐르는 것처럼 보일 수 있지만, 사실은 그렇지 않습니다. 이것은 사용 패턴이 누구의 태그에 관심이 있는지를 결정한다는 것을 보여줍니다.

일회성 풀은 커밋 히스토리가 한 그룹의 사람들(예: "커널 네트워킹 부분에 주로 관심 있는 사람들")에서 다른 그룹의 사람들("예: "2.6.21 릴리스에 대해 일반 소비를 위해 제안된 네트워킹 그룹의 세 번째 릴리스 후보")로 경계를 넘어서고 있음을 나타냅니다. 후자의 그룹은 일반적으로 전자의 그룹 내부에서 사용된 상세 태그에 관심이 없습니다 (그것이 "내부"를 의미하는 것입니다). 따라서 이 경우 태그를 자동으로 따라가지 않는 것이 바람직합니다.

네트워킹 사람들 사이에서, 그들 자신의 그룹 내부 태그를 교환하고 싶을 수 있지만, 그 워크플로우에서는 서로의 진행 상황을 원격 추적 브랜치를 가짐으로써 추적하는 것이 가장 일반적입니다. 다시 말하지만, 그러한 태그를 자동으로 따르는 휴리스틱은 좋은 것입니다.


Backdating Tags에 대하여
~~~~~~~~~~~~~~~~~~~~~~~~

다른 VCS에서 변경 사항을 가져왔고, 작업의 주요 릴리스에 대한 태그를 추가하고 싶다면, 태그 객체 안에 포함될 날짜를 지정하는 것이 유용합니다. 태그 객체의 그러한 데이터는 예를 들어 gitweb 인터페이스에서 태그 순서에 영향을 미칩니다.

미래의 태그 객체에 사용될 날짜를 설정하려면, 환경 변수 GIT_COMMITTER_DATE를 설정하십시오 (가능한 값에 대한 나중 논의를 참조하십시오. 가장 일반적인 형식은 "YYYY-MM-DD HH:MM"입니다).

예시:

------------
$ GIT_COMMITTER_DATE="2006-10-02 10:31" git tag -s v1.0.1
------------
