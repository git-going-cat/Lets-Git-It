git-push(1)
===========

NAME
----
git-push - 원격 ref와 연결된 객체들을 업데이트

SYNOPSIS
--------
[synopsis]
git push [--all | --branches | --mirror | --tags] [--follow-tags] [--atomic] [-n | --dry-run] [--receive-pack=<git-receive-pack>]
	 [--repo=<repository>] [-f | --force] [-d | --delete] [--prune] [-q | --quiet] [-v | --verbose]
	 [-u | --set-upstream] [-o <string> | --push-option=<string>]
	 [--[no-]signed | --signed=(true|false|if-asked)]
	 [--force-with-lease[=<refname>[:<expect>]] [--force-if-includes]]
	 [--no-verify] [<repository> [<refspec>...]]

DESCRIPTION
-----------

로컬 저장소의 하나 이상의 브랜치, 태그 또는 다른 ref를 원격 저장소에서 업데이트하고,
원격지에 이미 존재하지 않는 필요한 모든 데이터를 보냅니다.

가장 간단한 푸시 방법은 `git push <remote> <branch>`입니다.
`git push origin main`은 로컬 `main` 브랜치를 `origin`이라는 이름의 원격지의 `main` 브랜치로 푸시합니다.

`<repository>` 인자는 기본적으로 현재 브랜치의 업스트림(upstream)을 사용하거나,
설정된 업스트림이 없으면 `origin`을 사용합니다.

푸시할 브랜치, 태그 또는 다른 ref를 결정하기 위해 Git은 다음을 사용합니다.
(우선 순위 순서):

1. `<refspec>` 인자(예: `git push origin main`에서의 `main`)
   또는 `--all`, `--mirror`, `--tags` 옵션
2. 푸시할 저장소의 `remote.<name>.push` 설정
3. `push.default` 설정. 기본값은 `push.default=simple`이며,
   현재 브랜치와 같은 이름을 가진 브랜치로 푸시합니다.
   `push.default`에 대한 자세한 내용은 아래 <<CONFIGURATION,CONFIGURATION>> 섹션을 참조하십시오.

현재 브랜치의 업스트림을 설정하지 않았다면 `git push`는 실패할 수 있으며,
이는 `push.default`의 설정에 따라 달라집니다.
업스트림 설정 및 사용 방법에 대해서는 아래 <<UPSTREAM-BRANCHES,UPSTREAM BRANCHES>> 섹션을 참조하십시오.

푸시할 때마다 저장소에서 흥미로운 작업을 수행하도록 '훅(hooks)'을 설정할 수 있습니다.
linkgit:git-receive-pack[1] 매뉴얼 페이지를 참조하십시오.

[[OPTIONS]]
OPTIONS
-------
_<repository>_::
	푸시 작업의 대상이 되는 "원격" 저장소입니다. 이 인자는
	URL(아래 <<URLS,GIT URLS>> 섹션 참조) 또는
	원격지의 이름(아래 <<REMOTES,REMOTES>> 섹션 참조)일 수 있습니다.

`<refspec>...`::
	원본 객체를 어떤 대상 ref로 업데이트할지 지정합니다.
+
refspec의 형식은 `[+]<src>[:<dst>]`이며, 예를 들어 `main`,
`main:other`, 또는 `HEAD^:refs/heads/main`입니다.
+
_<src>_는 종종 푸시할 로컬 브랜치의 이름이지만,
어떤 "SHA-1 표현식"(linkgit:gitrevisions[7] 참조)이라도 될 수 있습니다.
+
_<dst>_는 원격지에서 어떤 ref를 업데이트할지 결정합니다. 임의의 표현식이 아닌
브랜치, 태그 또는 다른 ref의 이름이어야 합니다.
+
`+`는 선택 사항이며 `--force`와 동일한 작업을 수행합니다.
+
refspec은 완전히 확장된 형태(예: `refs/heads/main:refs/heads/main`)를 사용하여
정확한 원본과 대상을 지정하거나, 더 짧은 형태(예: `main` 또는
`main:other`)를 사용할 수 있습니다. refspec이 확장되는 규칙과
다양한 다른 특수 refspec 형식은 다음과 같습니다.
+
 * `:<dst>` 없이 _<src>_를 지정하면 `remote.<repository>.push` 설정이
   다른 _<dst>_를 지정하지 않는 한 _<src>_와 동일한 ref를 업데이트합니다.
   예를 들어, `main`이 브랜치인 경우 refspec
   `main`은 `main:refs/heads/main`으로 확장됩니다.
 * _<dst>_가 <repository> 원격지의 ref를 모호하지 않게 참조하는 경우,
   해당 ref로 확장합니다. 예를 들어, `v1.0`이 원격지의 태그인 경우
   `HEAD:v1.0`은 `HEAD:refs/tags/v1.0`으로 확장됩니다.
 * _<src>_가 `refs/heads/` 또는 `refs/tags/`로 시작하는 ref로 해석되면,
   이를 <dst> 앞에 붙입니다. 예를 들어, `main`이 브랜치인 경우
   `main:other`은 `main:refs/heads/other`로 확장됩니다.
 * `:` (또는 비-패스트-포워드 업데이트를 허용하려면 `+:` ) 같은
   특수 refspec은 Git에게 "일치하는" 브랜치를 푸시하도록 지시합니다. 로컬에
   존재하는 각 브랜치에 대해, 원격지에 같은 이름의 브랜치가 이미
   존재하는 경우 원격지 측이 업데이트됩니다.
 * _<src>_는 간단한 패턴 매칭을 나타내기 위해 `*`을 포함할 수 있습니다.
   이는 패턴과 일치하는 모든 ref를 매칭하는 glob과 유사하게 작동합니다.
   `<src>`와 `<dst>` 모두에 `*`이 하나만 있어야 합니다.
   원본의 일치 내용으로 *를 대체하여 refs를 대상으로 매핑합니다.
   예를 들어, `refs/heads/*:refs/heads/*`는 모든 브랜치를 푸시합니다.
 * `^`로 시작하는 refspec은 음수 refspec입니다.
   제외할 refs를 지정합니다. ref는 하나 이상의 양수 refspec과 일치하고
   음수 refspec과 일치하지 않으면 일치하는 것으로 간주됩니다.
   음수 refspec은 패턴 refspec일 수 있습니다.
   반드시 _<src>_만 포함해야 합니다.
   완전히 철자된 16진수 객체 이름은 지원되지 않습니다.
   예를 들어, `git push origin 'refs/heads/*' '^refs/heads/dev-*'`는
   `dev-`로 시작하는 것을 제외한 모든 브랜치를 푸시합니다.
 * _<src>_가 비어 있으면 원격 저장소에서 _<dst>_ ref를 삭제합니다.
   예를 들어, `git push origin :dev`는 `dev` 브랜치를 삭제합니다.
 * `tag <tag>`는 `refs/tags/<tag>:refs/tags/<tag>`로 확장됩니다.
    이는 기술적으로 `git push`의 특수 구문이며 refspec이 아닙니다.
    `git push origin tag v1.0`에서 `tag`와 `v1.0` 인자는 별개이기 때문입니다.
 * refspec을 모호하지 않게 확장할 수 없는 경우,
    시도했던 내용을 나타내는 오류 메시지를 표시하고
    `advice.pushUnqualifiedRefname` 설정에 따라
    푸시하려 했을 수 있는 refs/ 네임스페이스를 제안합니다.

모든 업데이트가 허용되지 않습니다. 자세한 내용은 아래 PUSH RULES를 참조하십시오.

`--all`::
`--branches`::
	모든 브랜치(즉, `refs/heads/` 아래의 ref)를 푸시합니다.
	다른 <refspec>과 함께 사용할 수 없습니다.

`--prune`::
	로컬 상응물이 없는 원격 브랜치를 제거합니다. 예를 들어,
	로컬 브랜치와 이름이 같은 원격 브랜치 `tmp`는 더 이상 존재하지 않으면
	제거됩니다. 이는 refspec도 존중합니다. 예를 들어,
	`git push --prune remote refs/heads/*:refs/tmp/*`는
	`refs/heads/foo`가 존재하지 않으면 원격 `refs/tmp/foo`가
	제거되도록 보장합니다.

`--mirror`::
	푸시할 각 ref를 나열하는 대신, `refs/` 아래의 모든 ref( `refs/heads/`,
	`refs/remotes/`, `refs/tags/`를 포함하되 이에 국한되지 않음)를
	원격 저장소에 미러링하도록 지정합니다. 새로 생성된 로컬
	ref는 원격지에 푸시되고, 로컬에서 업데이트된 ref는 원격지에서
	강제로 업데이트되며, 삭제된 ref는 원격지에서 제거됩니다.
	`remote.<remote>.mirror` 설정 옵션이 설정된 경우 이것이 기본값입니다.

`-n`::
`--dry-run`::
	실제로 업데이트를 보내는 것 외에 모든 작업을 수행합니다.

`--porcelain`::
	기계가 읽을 수 있는 출력을 생성합니다. 각 ref에 대한 출력 상태 줄은
	탭으로 구분되어 stdout으로 보내지고 stderr로는 보내지지 않습니다.
	ref의 전체 심볼릭 이름이 제공됩니다.

`-d`::
`--delete`::
	나열된 모든 ref가 원격 저장소에서 삭제됩니다. 이는 모든 ref 앞에
	콜론을 붙이는 것과 같습니다.

`--tags`::
	명령줄에 명시적으로 나열된 ref 외에도 `refs/tags` 아래의 모든 ref가
	푸시됩니다.

`--follow-tags`::
	이 옵션 없이 푸시될 모든 ref를 푸시하고, 원격지에 누락되었지만
	푸시되는 ref로부터 도달 가능한 커밋-ish를 가리키는
	어노테이션 태그도 푸시합니다. 이는 `push.followTags` 설정 변수로도
	지정할 수 있습니다. 자세한 내용은 linkgit:git-config[1]의
	`push.followTags`를 참조하십시오.

`--signed`::
`--no-signed`::
`--signed=(true|false|if-asked)`::
	수신 측에서 ref를 업데이트하기 위해 푸시 요청에 GPG 서명을 합니다.
	훅에서 확인하거나 기록할 수 있도록 합니다. 가능한 값은 다음과 같습니다:
`false`;;
`--no-signed`;;
	서명 시도가 이루어지지 않습니다.
`true`;;
`--signed`;;
	서명된 푸시를 서버가 지원하지 않으면 푸시가 실패합니다.
`if-asked`;;
	서명된 푸시를 서버가 지원하는 경우에만 서명합니다.
	`gpg --sign` 호출이 실패하면 푸시도 실패합니다.
	수신 측에 대한 자세한 내용은 linkgit:git-receive-pack[1]을 참조하십시오.

`--atomic`::
`--no-atomic`::
	가능한 경우 원격지에서 원자적 트랜잭션을 사용합니다.
	모든 ref가 업데이트되거나, 오류 시 어떤 ref도 업데이트되지 않습니다.
	서버가 원자적 푸시를 지원하지 않으면 푸시가 실패합니다.

`-o <option>`::
`--push-option=<option>`::
	주어진 문자열을 서버로 전송하며, 서버는 이를
	pre-receive 및 post-receive 훅으로 전달합니다. 주어진 문자열은
	NUL 또는 LF 문자를 포함해서는 안 됩니다.
	여러 개의 `--push-option=<option>`이 주어지면, 명령줄에 나열된 순서대로
	모두 다른 측으로 전송됩니다.
	명령줄에서 `--push-option=<option>`이 주어지지 않으면,
	`push.pushOption` 설정 변수의 값이 대신 사용됩니다.

`--receive-pack=<git-receive-pack>`::
`--exec=<git-receive-pack>`::
	원격지의 'git-receive-pack' 프로그램 경로입니다.
	ssh를 통해 원격 저장소로 푸시할 때 유용할 수 있으며,
	기본 `$PATH`의 디렉토리에 프로그램이 없는 경우 사용합니다.

`--force-with-lease`::
`--no-force-with-lease`::
`--force-with-lease=<refname>`::
`--force-with-lease=<refname>:<expect>`::
	일반적으로 `git push`는 로컬 ref가 덮어쓰려는 원격 ref의
	조상이 아닌 경우 업데이트를 거부합니다.
+
이 옵션은 현재 원격 ref의 값이 예상 값인 경우 이 제한을 재정의합니다.
`git push`는 그렇지 않으면 실패합니다.
+
이미 게시한 내용을 리베이스해야 하는 상황을 상상해 보세요.
원래 게시한 히스토리를 리베이스된 히스토리로 대체하기 위해
"반드시 패스트-포워드여야 한다"는 규칙을 우회해야 합니다.
리베이스하는 동안 다른 사람이 원래 히스토리를 기반으로 했다면,
원격지의 브랜치 팁이 해당 커밋으로 인해 진행될 수 있으며,
`--force`로 무조건 푸시하면 그들의 작업이 손실될 수 있습니다.
+
이 옵션은 업데이트하려는 히스토리가 리베이스하고 대체하려는 히스토리라고
말할 수 있게 합니다. 원격 ref가 당신이 지정한 커밋을 여전히 가리키고 있다면,
다른 사람이 해당 ref에 아무 작업도 하지 않았다고 확신할 수 있습니다.
이것은 명시적으로 잠그지 않고 ref에 대한 "리스"(lease)를 얻는 것과 같으며,
"리스"가 유효한 경우에만 원격 ref가 업데이트됩니다.
+
`--force-with-lease`만 단독으로 사용하고 세부 사항을 지정하지 않으면,
업데이트될 모든 원격 ref를 보호하며, 해당 ref의 현재 값이
해당 ref에 대한 원격 추적 브랜치의 값과 같아야 함을 요구합니다.
+
`--force-with-lease=<refname>`은 예상 값을 지정하지 않고 사용될 경우,
업데이트될 _<refname>_을 보호하며, 해당 ref의 현재 값이
해당 ref에 대한 원격 추적 브랜치의 값과 같아야 함을 요구합니다.
+
`--force-with-lease=<refname>:<expect>`는 업데이트될 _<refname>_을 보호하며,
해당 ref의 현재 값이 지정된 값 _<expect>_와 같아야 함을 요구합니다 (이는
그 ref에 대한 원격 추적 브랜치의 값과 다를 수 있으며, 이 형식을 사용할 때
그러한 원격 추적 브랜치가 없을 수도 있습니다). _<expect>_가 빈 문자열이면,
이름이 지정된 ref는 존재하지 않아야 합니다.
+
예상 값을 명시적으로 지정하는 `--force-with-lease=<refname>:<expect>`를
제외한 모든 형식은 아직 실험적이며, 이 기능에 대한 경험이 쌓이면서
의미가 변경될 수 있다는 점에 유의하십시오.
+
`--no-force-with-lease`는 명령줄의 이전의 모든 `--force-with-lease`를 취소합니다.
+
안전성에 대한 일반적인 참고 사항: 예상 값을 지정하지 않고 이 옵션을 제공하는
것, 즉 `--force-with-lease` 또는 `--force-with-lease=<refname>`과 같이
사용하는 것은 백그라운드에서 푸시할 원격지에 대해 `git fetch`를 암시적으로
실행하는 모든 것(예: 저장소에서 cronjob으로 `git fetch origin` 실행)과 매우
악영향을 미칩니다.
+
`--force`에 비해 제공하는 보호 기능은 후속 변경 사항이 덮어쓰이지 않도록
보장하는 것이지만, 백그라운드에서 ref를 업데이트하는 배경 프로세스가 있는
경우 이는 쉽게 우회될 수 있습니다. 우리가 참조할 수 있는 것은 백그라운드에서
업데이트되는 ref를 내가 보고 덮어쓰기를 원한다고 가정하는 원격 추적 정보뿐입니다.
+
편집기나 다른 시스템이 백그라운드에서 `git fetch`를 실행하는 경우, 다음으로
이것을 완화하는 한 가지 방법은 다른 원격지를 설정하는 것입니다:
+
----
git remote add origin-push $(git config remote.origin.url)
git fetch origin-push
----
+
이제 백그라운드 프로세스가 `git fetch origin`을 실행하면 `origin-push`의
참조는 업데이트되지 않으므로 다음과 같은 명령:
+
----
git push --force-with-lease origin-push
----
+
수동으로 `git fetch origin-push`를 실행하지 않으면 실패합니다. 이 방법은
물론 `git fetch --all`을 실행하는 것에 의해 완전히 무력화되며,
이 경우 비활성화하거나 더 번거로운 작업을 수행해야 합니다:
+
----
git fetch              # 원격지에서 'master' 업데이트
git tag base master    # 기본 지점을 표시
git rebase -i master   # 커밋 재작성
git push --force-with-lease=master:base master:master
----
+
즉, 덮어쓰기를 원하며 확인한 이전 버전의 코드를 위한 `base` 태그를 생성한 다음,
히스토리를 재작성하고, 마지막으로 원격 버전이 여전히 `base`인 경우 `master` 브랜치로
강제 푸시합니다. 로컬 `remotes/origin/master`가 백그라운드에서 업데이트되었는지
여부는 중요하지 않습니다.
+
대안으로, `--force-if-includes`를 보조 옵션으로 `--force-with-lease[=<refname>]`과
함께(즉, 원격지의 ref가 정확히 어떤 커밋을 가리켜야 하는지, 또는 원격지의 어떤
ref가 보호되는지 명시하지 않은 경우) "푸시" 시점에 지정하면, 백그라운드에서
암시적으로 업데이트되었을 수 있는 원격 추적 ref의 업데이트가 로컬에 통합되었는지
확인한 후 강제 업데이트를 허용합니다.

`-f`::
`--force`::
	일반적으로 `git push`는 푸시하려는 커밋의 조상이 아닌 브랜치를
	업데이트하는 것을 거부합니다.
+
이 옵션은 해당 검사를 비활성화하고, 아래 PUSH RULES의 다른 안전 검사,
그리고 `--force-with-lease`의 검사를 비활성화합니다.
	원격 저장소에서 커밋을 잃을 수 있으므로 주의해서 사용하십시오.
+
`--force`는 푸시되는 모든 ref에 적용되므로, `push.default`가
`matching`으로 설정되어 있거나 `remote.<name>.push`로 여러 푸시 대상이
구성된 경우 현재 브랜치 외의 ref(원격 counterpart보다 엄격하게 뒤처진
로컬 ref 포함)를 덮어쓸 수 있습니다. 단 하나의 브랜치로만 강제 푸시하려면
푸시하려는 refspec 앞에 `+`를 사용하십시오 (예: `git push origin +master`는
`master` 브랜치로 강제 푸시). 자세한 내용은 위 `<refspec>...` 섹션을 참조하십시오.

`--force-if-includes`::
`--no-force-if-includes`::
	원격 추적 ref의 팁이 로컬에 통합된 경우에만 업데이트를 강제합니다.
+
이 옵션은 기반이 되는 로컬 브랜치의 reflog 항목 중 하나에서
원격 추적 ref의 팁이 도달 가능한지 확인하는 검사를 활성화합니다.
이 검사는 원격지의 업데이트가 로컬에 통합되지 않은 경우 강제 업데이트를
거부하여 해당 업데이트가 로컬에 포함되었는지 확인합니다.
+
옵션이 `--force-with-lease`를 지정하지 않고 전달되거나,
`--force-with-lease=<refname>:<expect>`와 함께 지정되면,
"no-op"(아무 작업도 하지 않음)입니다.
+
`--no-force-if-includes`를 지정하면 이 동작이 비활성화됩니다.

`--repo=<repository>`::
	이 옵션은 _<repository>_ 인자와 동일합니다. 둘 다 지정되면
	명령줄 인자가 우선합니다.

`-u`::
`--set-upstream`::
	업데이트되었거나 성공적으로 푸시된 모든 브랜치에 대해,
	인자 없는 `linkgit:git-pull[1]` 및 기타 명령에서 사용되는
	업스트림(추적) 참조를 추가합니다. 자세한 내용은
	linkgit:git-config[1]의 `branch.<name>.merge`를 참조하십시오.

`--thin`::
`--no-thin`::
	이 옵션은 linkgit:git-send-pack[1]으로 전달됩니다. 송신자와 수신자가
	많은 객체를 공유하는 경우 thin 전송은 전송되는 데이터의 양을
	크게 줄입니다. 기본값은 `--thin`입니다.

`-q`::
`--quiet`::
	오류가 발생하는 경우를 제외하고, 업데이트된 ref 목록을 포함한
	모든 출력을 억제합니다. 진행 상태는 표준 오류 스트림으로
	보고되지 않습니다.

`-v`::
`--verbose`::
	자세한 정보 출력을 실행합니다.

`--progress`::
	진행 상태 보고는 일반적으로 표준 오류 스트림으로
	출력됩니다 (터미널에 연결된 경우, `-q`가 지정되지 않은 한).
	이 플래그는 표준 오류 스트림이 터미널에 연결되지 않은 경우에도
	진행 상태 보고를 강제합니다.

`--no-recurse-submodules`::
`--recurse-submodules=(check|on-demand|only|no)`::
	푸시할 리비전에 의해 사용되는 모든 서브모듈 커밋이
	원격 추적 브랜치에 있는지 확인하는 데 사용될 수 있습니다.
	가능한 값은 다음과 같습니다:
`check`;;
        Git은 푸시할 리비전에서 변경된 모든 서브모듈 커밋이
	적어도 하나의 서브모듈 원격지에 존재하는지 확인할 것입니다.
	어떤 커밋이라도 누락되면 푸시가 중단되고 0이 아닌 상태 코드로 종료됩니다.
`on-demand`;;
	푸시할 리비전에서 변경된 모든 서브모듈이 푸시됩니다.
	`on-demand`가 필요한 모든 리비전을 푸시하지 못하면
	중단되고 0이 아닌 상태 코드로 종료됩니다.
`only`;;
	모든 서브모듈이 푸시되고 슈퍼프로젝트는 푸시되지 않은 상태로 남겨집니다.
`no`;;
	서브모듈 재귀가 필요하지 않은 경우 `push.recurseSubmodules`
	설정 변수를 재정의합니다. `--no-recurse-submodules`를 사용하는 것과 유사합니다.

+
`on-demand` 또는 `only`를 사용할 때, 서브모듈에
`push.recurseSubmodules=(on-demand|only)` 또는 `submodule.recurse` 설정이
있는 경우 추가적인 재귀가 발생합니다. 이 경우 `only`는
`on-demand`로 처리됩니다.

`--verify`::
`--no-verify`::
	푸시 전 훅(linkgit:githooks[5] 참조)을 토글합니다.
	기본값은 `--verify`이며, 훅이 푸시를 방지할 기회를 줍니다.
	`--no-verify`를 사용하면 훅이 완전히 건너뛰어집니다.

`-4`::
`--ipv4`::
	IPv6 주소를 무시하고 IPv4 주소만 사용합니다.

`-6`::
`--ipv6`::
	IPv4 주소를 무시하고 IPv6 주소만 사용합니다.

OUTPUT
------

"git push"의 출력은 사용된 전송 방법에 따라 달라집니다. 이 섹션에서는
Git 프로토콜(로컬 또는 ssh를 통한)로 푸시할 때의 출력을 설명합니다.

푸시의 상태는 표 형식으로 출력되며, 각 줄은 단일 ref의 상태를 나타냅니다.
각 줄의 형식은 다음과 같습니다:

-------------------------------
 <flag> <summary> <from> -> <to> (<reason>)
-------------------------------

`--porcelain`이 사용되면, 출력의 각 줄은 다음과 같은 형식입니다:

-------------------------------
 <flag> \t <from>:<to> \t <summary> (<reason>)
-------------------------------

최신 상태인 ref의 상태는 `--porcelain` 또는 `--verbose` 옵션이
사용된 경우에만 표시됩니다.

_<flag>_::
	ref의 상태를 나타내는 한 글자:
(space);; 패스트-포워드로 성공적으로 푸시된 경우;
`+`;; 강제 업데이트가 성공한 경우;
`-`;; 삭제가 성공한 경우;
`*`;; 새 ref가 성공적으로 푸시된 경우;
`!`;; 거부되거나 푸시에 실패한 ref; 그리고
`=`;; 최신 상태로 푸시할 필요가 없는 ref;

_<summary>_::
	성공적으로 푸시된 ref의 경우, 요약은 ref의 이전 값과 새 값을
	`git log`의 인자로 사용할 수 있는 형식으로 보여줍니다
	(대부분의 경우 `<old>..<new>`이며,
	강제 비-패스트-포워드 업데이트의 경우 `<old>...<new>`입니다).
+
업데이트에 실패한 경우, 더 자세한 정보가 제공됩니다:
+
--
rejected::
	Git이 ref를 전혀 보내려고 시도하지 않았습니다. 일반적으로
	패스트-포워드가 아니며 업데이트를 강제하지 않았기 때문입니다.

remote rejected::
	원격 측에서 업데이트를 거부했습니다. 일반적으로 원격지에 있는 훅
	때문이거나, 원격 저장소에 다음과 같은 안전 옵션 중 하나가
	적용 중이기 때문입니다:
	`receive.denyCurrentBranch` (체크아웃된 브랜치로의 푸시에 대해),
	`receive.denyNonFastForwards` (강제 비-패스트-포워드 업데이트에 대해),
	`receive.denyDeletes` 또는 `receive.denyDeleteCurrent`.
	linkgit:git-config[1]을 참조하십시오.

remote failure::
	원격 측에서 ref의 성공적인 업데이트를 보고하지 않았습니다.
	원격 측의 임시 오류, 네트워크 연결 끊김 또는 기타 일시적인
	오류 때문일 수 있습니다.
--

from::
	푸시되는 로컬 ref의 이름으로, `refs/<type>/` 접두사가 제거된 것입니다.
	삭제의 경우, 로컬 ref의 이름은 생략됩니다.

to::
	업데이트되는 원격 ref의 이름으로, `refs/<type>/` 접두사가 제거된 것입니다.

reason::
	사람이 읽을 수 있는 설명입니다. 성공적으로 푸시된 ref의 경우,
	설명이 필요 없습니다. 실패한 ref의 경우, 실패 이유가 설명됩니다.

PUSH RULES
----------

안전 기능으로서, `git push` 명령은 데이터 손실을 우발적으로 방지하기 위해
특정 종류의 업데이트만 허용합니다.

브랜치와 태그는 다르게 사용될 의도이므로, 브랜치로 푸시할 때의 안전 규칙과
태그로 푸시할 때의 안전 규칙이 다릅니다. 다음 규칙에서 "업데이트"는
삭제 및 생성 외의 모든 수정을 의미합니다. 삭제 및 생성은
설정이나 훅에 의해 금지되지 않은 한 항상 허용됩니다.

1. 푸시 대상이 **브랜치** (`refs/heads/*`)인 경우:
   패스트-포워드 업데이트만 허용되며, 이는 대상이
   소스 커밋의 조상이어야 함을 의미합니다. 소스는 커밋이어야 합니다.
2. 푸시 대상이 **태그** (`refs/tags/*`)인 경우:
   모든 업데이트가 거부됩니다. 소스는 어떤 객체라도 될 수 있습니다.
3. 푸시 대상이 브랜치나 태그가 아닌 경우:
   * 소스가 트리 또는 블롭 객체인 경우, 모든 업데이트가 거부됩니다.
   * 소스가 태그 또는 커밋 객체인 경우, 패스트-포워드 업데이트는
     허용됩니다. 심지어 패스트-포워드되는 것이 커밋이 아니라,
     이전 태그(또는 커밋)가 대체하는 커밋과 패스트-포워드 관계인
     새 커밋을 가리키는 태그 객체인 경우에도 해당합니다.
     전혀 다른 태그로 태그를 교체하는 것도 허용되며,
     동일한 커밋을 가리키는 경우에도 그렇습니다. 또한,
     peeled 태그를 푸시하는 것도 허용됩니다. 즉, 기존 태그 객체가
     가리키는 커밋을 푸시하거나, 기존 커밋이 가리키는 새 태그 객체를
     푸시하는 것입니다.

`--force`를 전달하거나 refspec에 선택적인 선행 `+`를 추가하여
이 규칙을 재정의할 수 있습니다. 유일한 예외는 어떤 강제력도 브랜치가
비-커밋 객체를 수락하도록 만들 수는 없으며, 강제 푸시가 원격 저장소가
거부하도록 설정된 푸시를 허용하지 않는다는 것입니다.

훅과 설정도 이러한 규칙을 재정의하거나 수정할 수 있습니다.
예를 들어, linkgit:git-config[1]의 `receive.denyNonFastForwards` 및
`receive.denyDeletes`, 그리고 linkgit:githooks[5]의 `pre-receive` 및
`update`를 참조하십시오.

NOTE ABOUT FAST-FORWARDS
------------------------

업데이트가 브랜치(또는 더 일반적으로 ref)를 이전 커밋 A에서
다른 커밋 B로 변경하는 경우, B가 A의 후손인 경우에만
패스트-포워드 업데이트라고 합니다.

A에서 B로의 패스트-포워드 업데이트에서, 원래 커밋 A가 기반으로 했던
커밋 집합은 새 커밋 B가 기반으로 하는 커밋 집합의 부분 집합입니다.
따라서 역사를 잃지 않습니다.

반면에, 비-패스트-포워드 업데이트는 역사를 잃을 수 있습니다. 예를 들어,
당신과 다른 사람이 같은 커밋 X에서 시작했고, 당신이 커밋 B로 이어지는
히스토리를 구축했으며 다른 사람은 커밋 A로 이어지는 히스토리를 구축했다고 가정해 봅시다.
히스토리는 다음과 같이 보입니다:

----------------

      B
     /
 ---X---A

----------------

더 나아가, 다른 사람이 이미 당신 두 명이 원래 커밋 X를 얻었던
원격 저장소에 A로 이어지는 변경 사항을 푸시했다고 가정해 봅시다.

다른 사람이 수행한 푸시는 이전 커밋 X를 가리키던 브랜치를
커밋 A를 가리키도록 업데이트했습니다. 이것은 패스트-포워드입니다.

하지만 만약 당신이 푸시하려고 하면, A에 대한 커밋으로 (현재 A를
가리키는) 브랜치를 B 커밋으로 업데이트하려고 시도하게 됩니다. 이것은
패스트-포워드가 _아닙니다_. 그렇게 하면 B를 기반으로 누구나
작업을 시작하기 때문에 A 커밋의 변경 사항이 손실됩니다.

명령은 기본적으로 비-패스트-포워드 업데이트를 허용하지 않아
이러한 역사 손실을 방지합니다.

자신의 작업(X에서 B까지의 역사) 또는 다른 사람의 작업(X에서 A까지의 역사)을
잃고 싶지 않다면, 먼저 저장소에서 히스토리를 가져온 다음,
두 당사자의 변경 사항을 모두 포함하는 히스토리를 생성하고, 푸시해야 합니다.
