git-clone(1)
============

NAME
----
git-clone - 저장소를 새 디렉토리로 복제합니다.


SYNOPSIS
--------
[synopsis]
git clone [--template=<template-directory>]
	  [-l] [-s] [--no-hardlinks] [-q] [-n] [--bare] [--mirror]
	  [-o <name>] [-b <name>] [-u <upload-pack>] [--reference <repository>]
	  [--dissociate] [--separate-git-dir <git-dir>]
	  [--depth <depth>] [--[no-]single-branch] [--[no-]tags]
	  [--recurse-submodules[=<pathspec>]] [--[no-]shallow-submodules]
	  [--[no-]remote-submodules] [--jobs <n>] [--sparse] [--[no-]reject-shallow]
	  [--filter=<filter-spec> [--also-filter-submodules]] [--] <repository>
	  [<directory>]

DESCRIPTION
-----------

저장소를 새로 생성된 디렉토리로 복제하고, 복제된 저장소의 각 브랜치에 대해
원격 추적 브랜치를 생성합니다 (`git branch --remotes`로 볼 수 있음).
그리고 복제된 저장소의 현재 활성 브랜치에서 포크된 초기 브랜치를 생성하고 체크아웃합니다.

클론 후, 인자 없는 `git fetch`는 모든 원격 추적 브랜치를 업데이트하고,
인자 없는 `git pull`은 현재 마스터 브랜치가 있다면 (이것은 `--single-branch`가
주어졌을 때는 사실이 아님; 아래 참조) 원격 마스터 브랜치를 현재 마스터 브랜치로
머지합니다.

이 기본 설정은 `refs/remotes/origin` 아래의 원격 브랜치 헤드에 대한 참조를 생성하고,
`remote.origin.url` 및 `remote.origin.fetch` 설정 변수를 초기화함으로써 달성됩니다.


OPTIONS
-------
`-l`::
`--local`::
	복제할 저장소가 로컬 머신에 있을 때, 이 플래그는 일반 "Git aware" 전송
	메커니즘을 우회하고 `HEAD`와 objects 및 refs 디렉토리 아래의 모든 것을
	복사하여 저장소를 복제합니다.
	가능하면 공간을 절약하기 위해 `.git/objects/` 디렉토리 아래의 파일은
	하드링크됩니다.
+
저장소가 로컬 경로(예: `/path/to/repo`)로 지정되면, 이것이 기본값이며
`--local`은 사실상 아무 작업도 수행하지 않습니다. 저장소가 URL로 지정되면,
이 플래그는 무시됩니다 (그리고 로컬 최적화를 사용하지 않습니다).
`--no-local`을 지정하면 `/path/to/repo`가 주어졌을 때 기본값을 재정의하고,
일반 Git 전송을 대신 사용합니다.
+
저장소의 `$GIT_DIR/objects`가 심볼릭 링크를 가지고 있거나 심볼릭 링크 자체인 경우,
클론이 실패합니다. 이것은 심볼릭 링크를 역참조하여 의도하지 않은 파일 복사를
방지하기 위한 보안 조치입니다.
+
이 옵션은 보안상의 이유로 다른 사용자가 소유한 저장소에서는 작동하지 않으며,
클론이 성공하려면 `--no-local`이 지정되어야 합니다.
+
*참고*: 이 작업은 소스 저장소의 동시 수정과 경합할 수 있습니다.
_<src>_를 수정하는 동안 `cp -r <src> <dst>`를 실행하는 것과 유사합니다.

`--no-hardlinks`::
	로컬 파일시스템에 있는 저장소에서 복제 프로세스가 `.git/objects`
	디렉토리의 파일을 하드링크 대신 복사하도록 강제합니다.
	저장소의 백업을 만들려고 하는 경우 바람직할 수 있습니다.

`-s`::
`--shared`::
	복제할 저장소가 로컬 머신에 있을 때, 하드 링크를 사용하는 대신
	`.git/objects/info/alternates`를 자동으로 설정하여 소스 저장소와
	객체를 공유합니다. 결과 저장소는 초기에는 자체 객체를 가지지 않습니다.
+
참고: 이것은 잠재적으로 위험한 작업입니다. 그것이 무엇을 하는지 이해하지
못하면 *사용하지 마십시오*. 이 옵션으로 저장소를 클론한 다음
소스 저장소에서 브랜치를 삭제하거나 (또는 접근할 수 없는 커밋을 만드는
다른 Git 명령을 사용)하면 일부 객체가 접근할 수 없게 되거나 (또는 댕글링)
될 수 있습니다.
이러한 객체는 `git commit` (자동으로 `git maintenance run --auto`를 호출함)과
같은 일반 Git 작업에 의해 제거될 수 있습니다 (linkgit:git-maintenance[1] 참조).
이러한 객체가 제거되고 클론된 저장소에서 참조되었다면, 클론된 저장소는
손상될 것입니다.
+
`--shared`로 클론된 저장소에서 `--local` 옵션 없이 `git repack`을 실행하면,
소스 저장소에서 클론된 저장소의 팩으로 객체를 복사하여 `clone --shared`의
디스크 공간 절약을 제거합니다. 그러나 기본적으로 `--local` 옵션을 사용하는 `git gc`를
실행하는 것은 안전합니다.
+
`--shared`로 클론된 저장소의 소스 저장소 의존성을 끊고 싶다면,
`git repack -a`를 실행하여 소스 저장소의 모든 객체를 클론된 저장소의
팩으로 복사할 수 있습니다.

`--reference=<repository>`::
`--reference-if-able=<repository>`::
	참조 _<repository>_가 로컬 머신에 있으면, 참조 _<repository>_에서
	객체를 얻기 위해 `.git/objects/info/alternates`를 자동으로 설정합니다.
	기존 저장소를 대안으로 사용하면 복제되는 저장소에서 복사해야 할
	객체가 줄어들어 네트워크 및 로컬 스토리지 비용이 절감됩니다.
	`--reference-if-able`을 사용할 때, 존재하지 않는 디렉토리는
	클론을 중단하는 대신 경고와 함께 건너뜁니다.
+
참고: `--shared` 옵션의 참고를 참조하고 `--dissociate` 옵션도 참조하십시오.

`--dissociate`::
	`--reference` 옵션으로 지정된 참조 저장소에서 객체를 빌려오되,
	클론이 완료된 후 필요한 로컬 복사본을 만들어 더 이상 빌려오지 않도록 합니다.
	이 옵션은 이미 다른 저장소에서 객체를 빌려오고 있는 저장소에서
	로컬로 클론할 때도 사용할 수 있습니다. 새 저장소는 동일한 저장소에서
	객체를 빌려오도록 하며, 이 옵션으로 빌려오는 것을 중단할 수 있습니다.

`-q`::
`--quiet`::
	조용하게 작동합니다. 표준 에러 스트림으로 진행 상황이 보고되지 않습니다.

`-v`::
`--verbose`::
	자세하게 실행합니다. 표준 에러 스트림으로 진행 상황 보고에 영향을 미치지
	않습니다.

`--progress`::
	터미널에 연결되어 있지 않은 경우에도 `--quiet`이 지정되지 않은 한,
	기본적으로 표준 에러 스트림에 진행 상황 상태를 보고합니다. 이 플래그는
	표준 에러 스트림이 터미널로 리디렉션되지 않은 경우에도 진행 상황 상태를
	강제합니다.

`--server-option=<option>`::
	프로토콜 버전 2를 사용하여 통신할 때 주어진 문자열을 서버로 전송합니다.
	주어진 문자열은 NUL 또는 LF 문자를 포함해서는 안 됩니다. 서버 옵션의
	처리, 알 수 없거나 알려지지 않은 옵션을 포함한 처리는 서버별입니다.
	여러 `--server-option=<option>`이 주어지면, 명령줄에 나열된 순서대로
	모두 상대방에게 전송됩니다.
	명령줄에서 `--server-option=<option>`이 주어지지 않으면,
	`remote.<name>.serverOption` 구성 변수의 값이 대신 사용됩니다.

`-n`::
`--no-checkout`::
	클론 완료 후 `HEAD`를 체크아웃하지 않습니다.

`--no-reject-shallow`::
`--reject-shallow`::
	소스 저장소가 얕은 저장소인 경우 실패합니다.
	`clone.rejectShallow` 구성 변수를 사용하여 기본값을 지정할 수 있습니다.

`--bare`::
	'bare' Git 저장소를 만듭니다. 즉, _<directory>_를 생성하고
	관리 파일을 `<directory>/.git`에 배치하는 대신, _<directory>_
	자체를 `$GIT_DIR`로 만듭니다. 이는 당연히 체크아웃할 작업 트리가 없기
	때문에 `--no-checkout`을 내포합니다.
	또한 원격의 브랜치 헤드는 `refs/remotes/origin`으로 매핑하는 대신
	해당 로컬 브랜치 헤드로 직접 복사됩니다. 이 옵션을 사용하면,
	원격 추적 브랜치나 관련 구성 변수가 생성되지 않습니다.

`--sparse`::
	희소 체크아웃을 사용하며, 초기에 최상위 디렉토리의 파일만 존재합니다.
	linkgit:git-sparse-checkout[1] 명령어를 사용하여 필요에 따라 작업 디렉토리를
	확장할 수 있습니다.

`--filter=<filter-spec>`::
	부분 복제 기능을 사용하고 서버가 주어진 객체 필터에 따라
	유효한 객체의 하위 집합을 보내도록 요청합니다.
	`--filter`을 사용할 때, 제공된 _<filter-spec>_은 부분 복제 필터에
	사용됩니다.
+
`--filter=auto`를 사용하면, 필터 사양은 'promisor-remote' 프로토콜을 통해
자동으로 결정됩니다 (linkgit:gitprotocol-v2[5] 참조). 클라이언트가
허용하는 promisor 원격에 대해 서버에서 광고하는 필터 사양을 결합하여
(linkgit:git-config[1]의 `promisor.acceptFromServer` 구성 옵션 참조)
결정됩니다. 이를 통해 서버는 사용 가능한 promisor 원격에 대해 최적의
필터를 제안할 수 있습니다.
+
다른 필터 사양과 마찬가지로, "auto" 값은 구성에 영구적으로 저장됩니다.
이는 미래의 fetch가 서버의 현재 권장 사항에 계속 적응하도록 보장합니다.
+
다른 모든 사용 가능한 필터 사양에 대한 자세한 내용은
linkgit:git-rev-list[1]의 `--filter=<filter-spec>` 옵션을 참조하십시오.
+
예를 들어, `--filter=blob:none`은 필요할 때까지 모든 blob (파일 내용)을
필터링합니다. 또한 `--filter=blob:limit=<size>`는 _<size>_ 이상의 모든
blob을 필터링합니다.

`--also-filter-submodules`::
	저장소의 서브모듈에도 부분 복제 필터를 적용합니다.
	`--filter` 및 `--recurse-submodules`가 필요합니다. 이것은 `clone.filterSubmodules`
	설정 옵션을 설정하여 기본적으로 켤 수 있습니다.

`--mirror`::
	소스 저장소의 미러를 설정합니다. 이것은 `--bare`을 내포합니다.
	`--bare`에 비해, `--mirror`는 소스의 로컬 브랜치를 대상의 로컬 브랜치로
	매핑할 뿐만 아니라, 모든 ref (원격 추적 브랜치, notes 등 포함)를
	매핑하고 대상 저장소에서 `git remote update`를 실행할 때 이 모든 ref가
	덮어씌워지도록 하는 refspec 구성을 설정합니다.

`-o<name>`::
`--origin=<name>`::
	업스트림 저장소를 추적하기 위해 `origin` 원격 이름을 사용하는 대신,
	_<name>_을 사용합니다. config의 `clone.defaultRemoteName`을 재정의합니다.

`-b<name>`::
`--branch=<name>`::
	새로 생성된 `HEAD`를 복제된 저장소의 `HEAD`가 가리키는 브랜치 대신
	_<name>_ 브랜치를 가리키도록 합니다. non-bare 저장소에서는 이것이
	체크아웃될 브랜치입니다.
	`--branch`는 태그도 받을 수 있으며 결과 저장소에서 해당 커밋으로
	`HEAD`를 분리합니다.

`--revision=<rev>`::
	새 저장소를 생성하고, 주어진 수정본 _<rev>_로 이어지는 히스토리만
	(그 외에는 아무것도) 가져오고, 원격 추적 브랜치를 만들지 않고,
	로컬 브랜치를 만들지 않으며, `HEAD`를 _<rev>_로 분리합니다.
	인자는 커밋으로 분해되는 ref 이름 (예: `refs/heads/main` 또는
	`refs/tags/v1.0`) 또는 16진수 객체 이름일 수 있습니다.
	이 옵션은 `--branch` 및 `--mirror`와 호환되지 않습니다.

`-u<upload-pack>`::
`--upload-pack=<upload-pack>`::
	ssh를 통해 복제할 저장소에 접근할 때 원격 끝에서 실행되는 명령의
	기본값이 아닌 경로를 지정합니다.

`--template=<template-directory>`::
	템플릿이 사용될 디렉토리를 지정합니다.
	(linkgit:git-init[1]의 "TEMPLATE DIRECTORY" 섹션 참조.)

`-c<key>=<value>`::
`--config=<key>=<value>`::
	새로 생성된 저장소에 구성 변수를 설정합니다. 이는 저장소가
	초기화된 직후, 하지만 원격 히스토리를 가져오거나 파일을 체크아웃하기 전에
	효과를 발휘합니다. _<key>_는 linkgit:git-config[1]에서 예상하는 것과
	동일한 형식입니다 (예: `core.eol=true`). 동일한 키에 대해 여러 값이
	주어진 경우, 각 값이 구성 파일에 쓰여집니다. 이를 통해 예를 들어 origin
	원격에 추가적인 fetch refspec을 안전하게 추가할 수 있습니다.
+
현재 구현의 제약으로 인해 일부 구성 변수는 초기 fetch 및 체크아웃 후에만
효과를 발휘합니다. 효과를 발휘하지 않는 것으로 알려진 구성 변수는 다음과 같습니다:
`remote.<name>.mirror` 및 `remote.<name>.tagOpt`. 대신 해당 `--mirror` 및
`--no-tags` 옵션을 사용하십시오.

`--depth=<depth>`::
	지정된 커밋 수로 히스토리가 잘린 '얕은' 복제를 생성합니다.
	`--no-single-branch`가 제공되지 않는 한 `--single-branch`를 내포합니다.
	모든 브랜치의 팁 근처 히스토리를 가져오려면 `--no-single-branch`를
	제공하십시오. 서브모듈을 얕게 복제하려면 `--shallow-submodules`도
	함께 전달하십시오.

`--shallow-since=<date>`::
	지정된 시간 이후의 히스토리로 얕은 복제를 생성합니다.

`--shallow-exclude=<ref>`::
	지정된 원격 브랜치 또는 태그에서 도달할 수 있는 커밋을 제외한
	히스토리로 얕은 복제를 생성합니다. 이 옵션은 여러 번 지정할 수 있습니다.

`--single-branch`::
`--no-single-branch`::
	`--branch` 옵션 또는 원격 `HEAD`가 가리키는 기본 브랜치 중 하나로
	이어지는 히스토리만 복제합니다.
	결과 저장소로의 추가 fetch는 이 옵션이 초기 복제에 사용된 브랜치의
	원격 추적 브랜치만 업데이트합니다. 원격의 `HEAD`가 `--single-branch`
	복제가 만들어졌을 때 어떤 브랜치도 가리키지 않았다면, 원격 추적 브랜치가
	생성되지 않습니다.

`--tags`::
`--no-tags`::
	태그가 복제될지 여부를 제어합니다. `--no-tags`가 주어지면,
	옵션은 `remote.<remote>.tagOpt=--no-tags` 구성을 설정함으로써
	영구적이 됩니다. 이것은 향후 `git pull` 및 `git fetch`가 어떤
	태그도 따라가지 않도록 보장합니다. 후속 명시적 태그 fetch는 여전히
	작동합니다 (linkgit:git-fetch[1] 참조).
+
기본적으로 태그는 복제되며 `--tags`를 전달하는 것은 일반적으로
	아무 작업도 수행하지 않습니다. 이전 `--no-tags`를 상쇄하는 경우를
	제외하고는 말입니다.
+
`--single-branch`와 함께 사용하여 단일 복제된 브랜치만 참조하는 브랜치를
	복제하고 유지하는 데 사용할 수 있습니다. 이것은 예를 들어 검색
	인덱싱을 위해 일부 저장소의 기본 브랜치의 최소 복제를 유지하는 데 유용합니다.

`--recurse-submodules[=<pathspec>]`::
	클론이 생성된 후, 제공된 _<pathspec>_에 따라 서브모듈을 초기화하고 복제합니다.
	`=<pathspec>`이 제공되지 않으면, 모든 서브모듈이 초기화되고 복제됩니다.
	이 옵션은 여러 경로 사양이 있는 경우 여러 번 제공될 수 있습니다.
	결과 복제에는 _<pathspec>_이 제공되거나 (모든 서브모듈을 의미하는
	"`.`") 제공되지 않으면 "."이 `submodule.active`로 설정됩니다.
+
서브모듈은 기본 설정을 사용하여 초기화되고 복제됩니다. 이것은 클론이
	완료된 직후 `git submodule update --init --recursive <pathspec>`을
	실행하는 것과 같습니다. 이 옵션은 복제된 저장소가 작업 트리/체크아웃이
	없는 경우 (즉, `--no-checkout`/`-n`, `--bare` 또는 `--mirror` 중
	하나가 주어진 경우) 무시됩니다.

`--shallow-submodules`::
`--no-shallow-submodules`::
	복제되는 모든 서브모듈은 깊이 1의 얕은 복제본이 됩니다.

`--remote-submodules`::
`--no-remote-submodules`::
	복제되는 모든 서브모듈은 슈퍼프로젝트에 기록된 SHA-1을 업데이트하는
	대신, 서브모듈의 원격 추적 브랜치의 상태를 사용하여 서브모듈을 업데이트합니다.
	`git submodule update`에 `--remote`를 전달하는 것과 동등합니다.

`--separate-git-dir=<git-dir>`::
	복제된 저장소를 있어야 할 곳에 배치하는 대신, 지정된 디렉토리에
	복제된 저장소를 배치한 다음, 파일 시스템에 독립적인 Git 심볼릭 링크를
	거기에 만듭니다. 결과적으로 Git 저장소는 작업 트리와 분리될 수 있습니다.

`--ref-format=<ref-format>`::

`-j<n>`::
`--jobs=<n>`::

	`submodule.fetchJobs` 옵션으로 기본값이 설정됩니다.

_<repository>_::

EXAMPLES
--------

* 업스트림에서 복제:
+
------------
$ git clone git://git.kernel.org/pub/scm/.../linux.git my-linux
$ cd my-linux
$ make
------------


* 현재 디렉토리에서 빌려오는 로컬 복제를 만들고, 체크아웃은 하지 않음:
+
------------
$ git clone -l -s -n . ../copy
$ cd ../copy
$ git show-branch
------------


* 기존 로컬 디렉토리에서 빌려오면서 업스트림에서 복제:
+
------------
$ git clone --reference /git/linux.git \
	git://git.kernel.org/pub/scm/.../linux.git \
	my-linux
$ cd my-linux
------------


* 공개적으로 변경 사항을 게시하기 위해 bare 저장소를 생성:
+
------------
$ git clone --bare -l /home/proj/.git /pub/scm/proj.git
------------

* 다른 사용자의 로컬 저장소를 복제:
+
------------
$ git clone --no-local /home/otheruser/proj.git /pub/scm/proj.git
------------
