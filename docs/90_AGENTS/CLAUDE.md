<workflow>
## Working Process

<step number="1">
### Understand the Task

1. Identify task type (BE / FE)
2. Read corresponding guide
3. Ask if unclear

Task: "방 생성 API 추가"
→ Type: Backend
→ Guide: `CODING_STANDARD.md`, `REST_API.md`
</step>

<step number="2">
### Gather Context

1. Use `Read` to examine existing files
2. Check existing patterns in `com.gitcat.letsgitit.domain.*`
3. Review conventions

- Read: related Controller, Service, Entity
- Check: `global.exception.ErrorCode`
</step>

<step number="3">
### Plan the Work

1. For complex tasks (5+ steps), break down
2. Use TodoWrite for 3+ steps
3. Identify files to modify

**Typical backend chain**:
1. Entity (DB 연동 시)
2. Repository (interface + impl, 4-file DIP)
3. DTO (request/response record)
4. Service (interface + impl)
5. Controller (ControllerDocs + Controller)
6. Exception (domain-specific, CustomException 상속)
</step>

<step number="4">
### Implement

1. Follow Critical Rules in CODING_STANDARD.md
2. Follow package structure: `com.gitcat.letsgitit.domain.{domain}/...`
3. Use `ApiResponse` for all responses
4. Use `CustomException` + `ErrorCode` for exceptions
5. Use static factory method (`of`, `from`) instead of `@Builder`
</step>

<step number="5">
### Verify Quality

1. Check rules compliance
2. Run formatter before commit

- ✅ Entity: 정적 팩토리 메서드 (`of`/`from`), `@NoArgsConstructor(PROTECTED)`
- ✅ Service: interface + impl 분리
- ✅ Repository: 4-file DIP 패턴 (interface / impl / Jpa / Dsl)
- ✅ DTO: Java record
- ✅ Exception: CustomException 상속, ErrorCode static import
- ✅ Korean test names
</step>

<step number="6">
### Document

구현 완료 후 `docs/30_MODULES/BE/` 하위에 구현 문서를 작성하세요.
COMMON_RULES.md의 문서 템플릿을 따릅니다.
</step>
</workflow>
