# IMPLEMENTATION_START_SESSION_TRANSACTIONAL_SCOPE

## Background / Context

`SingleServiceImpl.startSession()`은 싱글 게임 시작 시 커맨드 셋 조회와 최고 점수 조회를 위해 RDB를 읽고, 동시에 Redis에 세션 캐시를 저장한다.

기존 구현은 메서드에 `@Transactional(readOnly = true)`가 선언되어 있었다. 런타임 오류는 없더라도 이 선언은 JPA에 "읽기 전용 메서드"라는 의미를 전달하므로, Redis 쓰기가 포함된 현재 유스케이스의 의도와 맞지 않았다.

---

## Decision

`startSession()`의 트랜잭션 선언을 `@Transactional(readOnly = true)`에서 일반 `@Transactional`로 변경했다.

이 메서드는 JPA 엔티티 변경을 직접 수행하지 않지만, 세션 시작이라는 하나의 유스케이스 안에서 Redis 쓰기가 포함되어 있으므로 읽기 전용 메서드로 표시하지 않는 편이 더 정확하다.

또한 `startSession()` 내부 처리 순서를 "DB 조회 완료 → Redis 세션 저장 → 응답 반환"으로 정리했다.

---

## Why

`readOnly = true`는 단순히 "DB 쓰기만 없으면 된다"는 의미가 아니라, 해당 메서드가 읽기 전용 흐름이라는 의도를 드러내는 선언이다. 따라서 외부 저장소 쓰기가 포함된 메서드에는 맞지 않는다.

현재 구조에서는 DB 읽기와 Redis 쓰기가 한 유스케이스로 묶여 있으므로, 우선 일반 트랜잭션으로 의미를 바로잡는 쪽이 가장 단순하고 안전하다.

Redis 저장보다 뒤에 DB 조회가 남아 있으면, Redis에는 세션이 저장됐지만 이후 DB 조회 예외로 전체 요청은 실패하는 부분 실패 상태가 생길 수 있다. 세션 TTL이 있어 치명적이지는 않더라도, 응답 성공 직전에 Redis 저장이 일어나도록 순서를 두는 편이 논리적으로 더 일관적이다.

---

## Caution

- Redis는 JPA 트랜잭션에 참여하지 않으므로, 이 변경이 Redis 저장의 원자성을 보장하는 것은 아니다.
- 이후 세션 생성 흐름을 더 엄격하게 분리할 필요가 생기면 "DB 읽기"와 "Redis 세션 저장"을 별도 단계로 나누는 리팩터링을 검토할 수 있다.
- 현재 순서 조정으로 "Redis 저장 후 DB 조회 실패" 경로는 제거됐지만, 반대로 Redis 저장 자체가 실패하면 요청은 실패한다. 이는 세션 생성 응답과 캐시 상태를 맞추기 위한 의도된 동작이다.
- `selectCommandSet()`은 현재 난이도별 command set 전체를 메모리에 올린 뒤 랜덤 인덱스로 하나를 고른다. 지금은 게임 데이터셋 수가 작고 제한적이라 허용 가능하지만, 세트 수가 커지면 `COUNT + OFFSET` 조회나 DB 단 랜덤 선택 방식으로 바꾸는 것이 더 적절하다.

---

## Test Plan

- `startSession()` 호출 시 기존과 동일하게 세션 ID, 커맨드 셋, 최고 점수가 정상 반환되는지 확인
- Redis에 세션 캐시가 정상 저장되는지 확인
- 트랜잭션 선언 변경으로 조회 쿼리 및 응답 구조에 회귀가 없는지 확인
- DB 조회 예외 상황에서 Redis 세션이 생성되지 않는지 확인
