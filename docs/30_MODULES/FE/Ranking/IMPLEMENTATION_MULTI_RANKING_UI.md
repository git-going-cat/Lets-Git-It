# 멀티 랭킹 UI 구현

## Background / Context

랭킹 모달은 싱글 랭킹 중심으로 구현되어 있었고, 멀티 모드 중 협력 랭킹은 백엔드 조회 조건과 화면 표시 요구사항이 맞지 않아 정상 조회가 되지 않았다.

운영 백엔드는 협력 랭킹 조회 시 `mapName` 파라미터를 필수로 요구한다. 따라서 프론트는 협력 랭킹 탭 진입 시 조회 가능한 협력 맵 목록을 가져오고, 선택된 맵의 `mapName`, `difficulty`, `mapId`를 랭킹 API 파라미터와 React Query 캐시 키에 함께 반영해야 한다.

또한 협력 랭킹은 팀 기록이므로 일반 점수 컬럼만으로는 원인을 비교하기 어렵다. 맵, 오타, 리셋 정보를 목록 컬럼으로 분리해 같은 맵 기준에서 기록을 비교할 수 있어야 한다.

## Decision

협력 랭킹 조회 조건을 `CoopRankingQuery`로 모델링하고, `fetchCoopRanking` / `fetchCoopRankingHistory`에서 `mapName`, `difficulty`, `mapId`를 전달하도록 변경했다.

랭킹 feature가 멀티 feature의 방 생성용 맵 훅을 직접 import하지 않도록, 랭킹 feature 내부에 협력 랭킹 맵 목록 조회 API와 `useCoopRankingMaps` 훅을 추가했다. REST 응답은 공통 `apiResponseSchema`와 Zod 스키마로 검증하고, 검증 실패 시 React Query error state로 전달한다.

협력 랭킹 모드에서는 상단 맵 버튼을 제거하고, 목록 헤더의 `맵` 컬럼 옆 드롭다운으로 맵을 선택한다. 드롭다운 항목은 `맵 이름 + 별 난이도` 형식으로 표시한다.

목록 행에는 협력 랭킹 전용 컬럼으로 `맵`, `오타`, `리셋`, `기록`을 표시한다. 팀원 목록은 보조 텍스트로 유지해 랭킹 행의 주요 비교 기준이 컬럼에 정렬되도록 했다.

## Why

협력 랭킹의 필수 조회 조건을 UI 상태와 캐시 키에 포함하지 않으면, 맵을 바꿔도 이전 맵 결과가 재사용되거나 백엔드에서 `MISSING_PARAMETER`가 발생한다.

맵 목록 조회를 랭킹 feature 내부로 분리한 이유는 feature 간 직접 의존을 줄이고, 랭킹 화면에서 필요한 데이터 계약을 랭킹 스키마로 명확히 검증하기 위해서다.

## Caution

협력 랭킹 API가 `mapName` 대신 `mapId`만 요구하도록 변경되면 `CoopRankingQuery`와 API 파라미터를 함께 조정해야 한다.

맵 난이도는 숫자 기준으로 별을 렌더링한다. 백엔드가 문자열 난이도로 바꾸면 Zod 검증에서 실패한다.

## Test Plan

- 협력 랭킹 탭 진입 시 협력 맵 목록 요청이 성공하는지 확인한다.
- 맵 드롭다운에서 다른 맵을 선택하면 랭킹 요청 파라미터에 `mapName`, `difficulty`, `mapId`가 반영되는지 확인한다.
- 협력 랭킹 목록에서 맵, 오타, 리셋 컬럼이 행별로 정렬되어 보이는지 확인한다.
- 싱글, 기여도, 타임어택 랭킹 탭의 기존 조회와 스크롤 동작이 유지되는지 확인한다.
- `npm run lint`와 `npm run build`를 실행한다.
